# Designing a reviewer role

Apply these when adding a reviewer — the simplicity reviewer on the roadmap, an expert or domain reviewer — or reshaping one. They generalize from red-team and the extension architect; adjust them as evidence accumulates.

1. **Audit trail of priors.** A review that compares the artifact with existing documents carries a `Checked against:` line naming specific anchors: file and section, ADR slug, spec filename. Bare `CLAUDE.md` doesn't count. It is required even when nothing is flagged, because otherwise "nothing flagged" cannot be told apart from "didn't read the priors".
2. **Validate mechanics and judgment separately.** A new role passes live validation only if (a) its output is mechanically compliant — header, findings format, `Blocking: N`, identity, verdict, `Checked against:` — and (b) the owner judges that the critique engages with the artifact rather than performing engagement. Compliant structure that reports nothing fails (b) unless the artifact really is trivial.
3. **Registry fields before they diverge.** Add a field to `.claude/agent-config.json` when the first role needs it, even if every role has the same value: retrofitting it later costs more.
4. **Tripwires for quality worries.** A validation plan says how a known worry would be detected. A tripwire fits when the worry is tied to a specific failure mode of the role, shows in the review's output, and is judged as a pattern across N PRs. A rule that is decidable on the review text alone, has no false positives in its final form, and whose failure signature is its whole meaning (for example "a review body contains an absolute home path") fires at N=1. Tripwires are manual review items in the spec's validation section.
5. **Wiring.** A role needs a GitHub App with its key at `$HOME/.config/gcscode/gcscode-<role>.pem`, an entry in `.claude/agent-config.json`, an agent file in `.claude/agents/` (instructions, pinned model ID, header, token slug, findings format ending `Blocking: N`), a place in the review-loop skill's dispatch (the spec/ADR table and step 3, or the feature-PR steps) — the skill names every role it dispatches — and, if its verdict should gate merges, a change to `.github/workflows/auto-merge.yml`. Dispatch it once by name before relying on it (see the reload caveat in [SKILL.md](SKILL.md)).
