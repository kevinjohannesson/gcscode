# Out of scope (for this step)

This is the canonical list of things intentionally NOT built in the current extension-architecture iteration. When an agent or contributor is tempted to add one of these, the answer is "not yet — re-confirm before reopening." Add items here when you defer work; remove them when the work lands.

See `docs/decisions/ADR-0003-plugin-api-refinements.md` for the load-bearing reasoning behind the manifest-shaped deferrals.

## Extension machinery

- **Declarative `contributes` manifest.** No statically-parseable list of contributions (commands, views, status bar items, etc.) that the host can read without executing `activate()`. Imperative `register*` calls inside `activate(context)` are the contract for runtime registration. Note: per-extension descriptive metadata (`displayName`, `version`, `description?`) IS structured on `Extension.manifest` per ADR-0007; the deferral here is specifically the `contributes` arrays — declarative lists of commands / views / keybindings / status bar items as data, parseable without running `activate()`. _Trigger to revisit:_ a settings UI that toggles individual contributions, the first untrusted extension module, or the first third-party producer-consumer pair. (ADR-0003, ADR-0007)
- **Activation events / lazy activation.** No `activationEvents: ["onCommand:..."]`. Extensions activate eagerly — at boot, or when re-enabled at runtime via `manager.setEnabled(id, true)` post-B2b. Never lazily on event. _Trigger to revisit:_ cold-start time becomes a problem (~50+ extensions). (ADR-0003)
- **Extension activation ordering / dependency declaration.** No `extensionDependencies` manifest field, no topological sort, no "I require X to be active before me" declaration. Today extensions activate in `bundledExtensions` array order; consumers of `host.extensions.getExtension(id)?.exports` handle undefined defensively. _Trigger to revisit:_ the first service→service edge that must resolve during `activate()`, OR third-party producer/consumer pair, OR manifest-driven enable persistence. ADR-0012 sharpened the first clause from "first ordering bug" — an ordering bug is the symptom, an activate-time edge between two service extensions is the condition that produces it. Note what does NOT fire it: the MAVLink adapter resolves the assets service lazily per inbound message, so the `extension-sitl` → `extension-assets` chain creates no activation-time edge. **Shipped and measured 2026-10-21** ([`specs/2026-10-21-asset-abstraction-v0.md`](specs/2026-10-21-asset-abstraction-v0.md)): against a live stream, disabling the service mid-stream left the adapter warning once and continuing, and re-enabling it re-claimed within about a second with no reload. That is the harder case than boot order — the service was absent when a heartbeat arrived and appeared afterwards — so lazy resolution plus degrade-when-absent is now the demonstrated alternative to declaring a dependency rather than the intended one. Boot order itself is covered structurally rather than empirically: activation is synchronous and completes before the first message arrives, and no test asserts the pair's relative position. (ADR-0005, [ADR-0012](decisions/ADR-0012-service-extensions-vs-host-namespaces.md))
- **Programmatic extension enable/disable API.** No `host.extensions.setEnabled(id, bool)` for third-party extensions to toggle other extensions. Today only the workbench built-in (which has direct `ExtensionManager` access) drives enable/disable, in response to user UI interaction via the extensions panel. _Trigger to revisit:_ first third-party consumer that needs programmatic toggle of a sibling extension (e.g. a "preset" extension that activates a curated set of others). When triggered, the API likely lives on `host.extensions.*` and requires capability-declaration plumbing first.
- **Capability / permission declarations.** No declared-capabilities schema and no runtime enforcement. The `ExtensionHost` is the seam where this will plug in (see ADR-0002); do not pre-build the schema. _Trigger to revisit:_ the first untrusted extension module. (ADR-0003)
- **Hot module reload for extensions.** Changing an extension requires a full page refresh (same as any Vite change to shell code).
- **`registry.deactivateAll()` / bulk teardown.** `deactivate(extensionId)` is single-extension only. Callers that want to tear down every active extension iterate per-extension. _Trigger to revisit:_ a host-driven shutdown path or a test harness that needs guaranteed reverse-activation order across extensions.
- **Additional contribution kinds beyond views, status bar items, commands, and keybindings.** Today: four `register*` methods on `ExtensionHost` (`registerView`, `registerStatusBarItem`, `registerCommand`, `registerKeybinding`) plus the verb `executeCommand`. Add another (e.g. `registerMenuItem`, `registerPaletteEntry`) when there is a real consumer; do not pre-declare surfaces that have no contributor.
- **Numeric `priority` for status bar items.** No `priority` field on `StatusBarItemContribution`; ordering within an alignment side follows registration order. _Trigger to revisit:_ a third-party extension wants to insert between two first-party items.
- **Event bus, themes, i18n.** Extensions have nine verbs today: `host.window.registerView`, `host.window.registerStatusBarItem`, `host.commands.registerCommand`, `host.keybindings.registerKeybinding`, `host.commands.executeCommand`, `host.extensions.getExtension`, `host.configuration.registerConfiguration`, `host.configuration.getConfiguration`, and `host.configuration.onDidChangeConfiguration`. The remaining items are deferred until there is a real consumer (e.g. events bus, theme switcher, localized string lookup). (Settings landed in `specs/2026-05-18-configuration-system-v1.md`.)
- **Per-extension persistent state (`globalState` / `workspaceState`).** No host-provided storage on `ExtensionContext` for extension-owned key/value persistence. Extensions can reach for `localStorage` directly today; none have. _Trigger to revisit:_ first extension needing persistent state, or a settings system that should also expose extension-scoped storage. **Status note 2026-05-18:** the settings substrate landed in [`specs/2026-05-18-configuration-system-v1.md`](specs/2026-05-18-configuration-system-v1.md); the half-trigger about "settings system that should also expose extension-scoped storage" did NOT fire — settings v1 is user-visible schema'd state, not extension-owned opaque storage. The row stays deferred.
- **Quick pick advanced features.** `QuickPickItem.kind` (separators / group headers), `iconPath`, `buttons`, `picked`, `alwaysShow`. `QuickPickOptions.canPickMany` (multi-select), `matchOnDescription`, `matchOnDetail`, `ignoreFocusOut`, `onDidSelectItem`. Async items (`Promise<T[]>`). `CancellationToken` parameter. Modal stacking (multiple concurrent overlays). _Trigger to revisit:_ first consumer wants any specific field — add per-field, do not bundle.
- **Third-party sandboxing.** No iframe / worker isolation, CSP hardening, or trusted-types. All extensions currently execute in the shell's JS realm. Safe because all extensions are first-party + in-tree. _Status note (containment, 2026-10-20):_ host-side activation-failure containment removes the boot-halt class — one extension's failed `activate` no longer costs the operator the app — but it provides no isolation. A misbehaving extension can still hang, leak, or exhaust the shared realm.
- **Dynamic / runtime extension loading.** Extensions are imported by package name at shell build time. Filesystem discovery, extension marketplaces, runtime `import(...)` are all deferred.
- **`when` clauses (visibility / enablement of contributions).** No expression evaluator or evaluation context for conditionally showing or enabling commands in menus, palette entries, or status bar items. _Trigger to revisit:_ the first contribution that wants to hide or disable itself based on host state (file open, focus, settings value, etc.) — _not_ merely the first menu/palette landing.
- **Async cancellation tokens.** No `CancellationToken` (or equivalent) for long-running command callbacks or future async APIs. _Trigger to revisit:_ the first command (or future async kind) that takes long enough to be worth cancelling.
- **Sequential / chord keybindings.** No support for `Ctrl+K Ctrl+S`-style two-step keybindings; one combo per registration. _Trigger to revisit:_ a real consumer wants chord shortcuts (typically a settings/file palette).
- **User-overridable keybindings.** No `keybindings.json`-equivalent override file or settings UI. Extension-registered keybindings are the only source. _Trigger to revisit:_ users complain about extension keybinding conflicts, or a settings system lands. **Status note 2026-05-18:** the settings substrate landed in [`specs/2026-05-18-configuration-system-v1.md`](specs/2026-05-18-configuration-system-v1.md); the second half of the trigger has fired. The user-overridable-keybindings concept still needs its own design — this status note marks the row as ready-for-re-evaluation, not auto-in-scope.
- **Cross-platform key aliasing (`Mod`, `mac:` overlay).** Literal `Ctrl` / `Cmd` only; no automatic platform mapping. _Trigger to revisit:_ first Mac user reports an extension keybinding doesn't work as expected (e.g. expecting `Cmd+S`, getting nothing because the registered binding is `Ctrl+S`).
- **Focus-aware keybinding suppression (broader).** A modal-pause hook (`modalState.active` signal; dispatcher early-returns when true) is in for the palette's needs. Remaining cases — text-input introspection in extension-rendered forms, `when`-clause-based gating, modal stacking (multiple concurrent overlays) — still deferred. _Trigger to revisit:_ first extension-rendered text input where the dispatcher's keydown interception fires a command unintentionally, or a `when`-clause use case landing.
- **Versioning, dependency resolution, peer-compat checks.** Not applicable — everything is `workspace:*`.
- **Animated camera transitions on the map.** No `flyTo` / `easeTo` exposed on `MapApi`; camera writes are instant via `jumpTo`. _Trigger to revisit:_ first consumer needing a pan-to-selection animation, or the follow-mode iteration. See `docs/specs/2026-05-03-map-and-flight-overlay.md`.
- **Camera coordination between map consumers.** No locks, priorities, or contention API. Multiple consumers writing the camera in the same tick: last-write-wins. _Trigger to revisit:_ first real conflict between two extensions trying to control the camera.
- **Layer ordering / z-index API on the map.** `MapApi.registerLayer` does not accept an order/priority field; layers paint in registration order. Mirrors the status-bar `priority` deferral. _Trigger to revisit:_ third-party wants to insert between two first-party layers.
- **Cross-extension Svelte context constants published by the host.** Today consumers re-declare context keys (e.g. `'gcscode.map.maplibre'`) as string literals matching the producer's contract — runtime sibling imports are forbidden by ADR-0005. _Trigger to revisit:_ a third consumer surface where re-declaration becomes brittle, OR a capability-declaration system that publishes named constants centrally.
- **Theme tokens / CSS-variable system for extension styling.** No `--gcscode-*` CSS variables exposed; component-path map controls and (future) webview content cannot match host visuals from extension code. _Trigger to revisit:_ webview wing iteration (canonical theming consumer), or the parallel UI brainstorm landing on a documented design system that wants extension reach. When triggered, follow VS Code's pattern: CSS variables only, no component/utility classes. (See `docs/specs/2026-05-03-map-controls.md`.)
- **Numeric `priority` ordering for map controls.** No `priority` field on `MapControlContribution`; ordering within a corner follows registration order. Mirrors the existing status-bar and layer `priority` deferrals. _Trigger to revisit:_ third-party wants to insert between two first-party controls.
- **Hover / active state customization on declarative controls.** Host renders one button visual style; extensions cannot override colors, sizing, or drop-shadow on the declarative path. _Trigger to revisit:_ a control needs a different state (e.g. destructive action wants red hover) — likely surfaces alongside the theme-tokens iteration.
- **SVG sanitization for extension-provided icons.** Extension SVG (`{ kind: 'svg', svg }`) is inserted as-is via `{@html}`. Safe today because all extensions are first-party (per the existing third-party-sandboxing row above). _Trigger to revisit:_ rolls in with the webview / sandboxing iteration.
- **Settings editor UI.** No overlay, no widgets, no JSON view. Operators flip values via browser devtools (`localStorage` blob + reload). _Trigger to revisit:_ operator UX feedback (specifically: a silent-schema-rejection failure causes confusion) OR a second real setting consumer landing. Substrate: [`specs/2026-05-18-configuration-system-v1.md`](specs/2026-05-18-configuration-system-v1.md).
- **Workspace + WorkspaceFolder configuration targets.** `ConfigurationTarget.Workspace` and `WorkspaceFolder` are exposed in the enum but `update` rejects the Promise with `'Target not supported in v1'`. `inspect` does not take a target parameter; its return shape extends additively when workspace scope lands. _Trigger to revisit:_ a workspace or workspace-folder concept lands in gcscode.
- **Settings cleanup for uninstalled extensions.** Persisted values for removed extensions accumulate as orphans in the configuration blob. _Trigger to revisit:_ orphan count becomes observable, OR an extension-uninstall UX is built.
- **Settings schema migration hooks.** Schema-incompatible persisted values fall back to the new default + log a warning. No declared migration path. _Trigger to revisit:_ a real consumer's schema change loses user state in a way that warrants a hook.
- **Live-sync of devtools-edited localStorage.** No `window.addEventListener('storage', …)` listener; devtools edits require a reload to take effect. _Trigger to revisit:_ cross-tab use surfaces OR operator workflow needs live-reload.
- **Visible boot-time signal for schema-validation rejection.** When `registerConfiguration` finds a persisted value that violates the schema, it logs `console.warn` and falls back to default. No status-bar or boot-banner UI surface communicates this to the operator. The same fix-class also surfaces persistence-failure rejections from `update()` (quota / disabled / security context). _Trigger to revisit:_ first operator-confusion report from a silent-rejection event.
- **Generalized `Event<T>` substrate.** `onDidChangeConfiguration(listener: (e) => void): Disposable` is the gcscode event-shape convention. No shared `Event<T>` primitive yet. _Trigger to revisit:_ a second event-shaped API lands and either reuses the same signature (no substrate needed) or wants richer semantics (filtering, replay, priority — substrate iteration warranted).
- **Cross-extension settings write capability gating.** Any extension can `update` any registered key in v1. No capability declaration / per-extension scoping. _Trigger to revisit:_ the broader capability-declaration iteration (ADR-0003) OR the first untrusted extension iteration.
- **Dynamic `import()` and JavaScript files across the boundary.** The restricted-imports rules in `eslint.config.ts` see static `import` and `export … from` only, so `await import('@gcscode/extension-map')`, or a relative path into another package, is lint-clean from an extension and from the shell alike. They also lint `.ts` and `.svelte` files only. No extension package and nothing in the shell uses either today: the only `.js` file under `packages/extension-*` and `packages/shell` is `packages/shell/svelte.config.js`, build configuration, and the only `import(` there is a JSDoc type in that file. _Trigger to revisit:_ the first dynamic `import()` or `.js`/`.mjs` source file in an extension package or the shell; Phase B3's hot module reload is the likeliest. ([ADR-0005](decisions/ADR-0005-extension-boundaries.md), [ADR-0012](decisions/ADR-0012-service-extensions-vs-host-namespaces.md))
- **Versioning of a service extension's contract.** A service's API type is an unversioned contract shared through `workspace:*`; VS Code's equivalent precedent (`getExtension('vscode.git').exports.getAPI(1)`) is a version broker, and gcscode skips that layer. _Trigger to revisit:_ extensions ship independently, or a service contract gains a second implementation — which is also the trigger for moving a contract to a neutral package. ([ADR-0012](decisions/ADR-0012-service-extensions-vs-host-namespaces.md), ADR-0005)
- **Service-extension granularity.** Nothing decides whether one service extension exposes several related ports or each port gets its own package. The costs that scale are per-service (one activation edge, one lookup site, one ordering comment), so the stated steer is to prefer fewer, coarser services. _Trigger to revisit:_ the asset iteration, which must choose whether the live-state port shares `extension-assets` or gets its own package. ([ADR-0012](decisions/ADR-0012-service-extensions-vs-host-namespaces.md))
- **Re-enable semantics for disabled service extensions, in general.** Each service documents its own: ADR-0011 decides that the asset registry keeps nothing across its own teardown (sources disposed, registry emptied, held handles inert), while `mapApi` keeps consumer-owned registrations. No host-level rule covers the class. _Trigger to revisit:_ a third service whose state does not fit either posture. ([ADR-0012](decisions/ADR-0012-service-extensions-vs-host-namespaces.md), [ADR-0011](decisions/ADR-0011-asset-vocabulary-and-registry.md))

- **General operator-facing notification primitive.** No `host.window.showMessage`-equivalent; the activation-failure indicator is a single-purpose host-owned surface. Three consumers are already known: that indicator, the existing "Visible boot-time signal for schema-validation rejection" row, and [ADR-0012](decisions/ADR-0012-service-extensions-vs-host-namespaces.md)'s degrade path. _Trigger to revisit: **fired 2026-10-20.**_ The trigger was "the first extension that actually degrades in the field"; `extension-flight-overlay` now degrades on any Map disable, so an operator turning Map off gets a map with no drone overlay and no explanation anywhere in the UI — the third consumer is real, not prospective. Amend the schema-validation-signal row to cross-reference this one when it lands.
- **In-place retry of a failed activation, and the activate-idempotency contract it requires.** Re-entering `activate()` on a live module is unsafe — `extension-sitl`'s `openClient` assigns `client` without closing the previous socket — so retry happens only on reload. Making a button safe means a stated rule in `@gcscode/extension-api` that `activate` is safe to re-enter, plus an audit: a constraint binding every future extension, which is why it lives here rather than in one spec's Non-goals. _Trigger to revisit:_ an operator workflow where reload is too expensive, or the first extension whose activation is provably idempotent.
- **Async `activate`, and awaited activation.** A thenable return is an activation error: the host observes the rejection, revokes, disposes and records it. Supporting async activation means awaiting it, which changes the registry's contract and the boot sequence. The nearest existing row, "Async cancellation tokens", is a different concern. _Trigger to revisit:_ the first extension whose activation genuinely cannot complete synchronously — the on-deck SITL listener work is the likely source.
- **Retry backoff or auto-disable for repeatedly failing extensions.** Retry-every-reload is the whole policy; there are no counters. _Trigger to revisit:_ an extension whose failure path is expensive enough that retrying every load costs real startup time.
- **Cleanup of contributions an extension registered into another extension's registry.** Host-side containment cannot see or dispose them: `extension-flight-overlay` takes five of its six disposables from `extension-map`, so a failed activation leaves them live. Fixing it needs either a teardown contract on service-extension APIs or a host-mediated registration path. _Trigger to revisit:_ the first operator-visible consequence — a stale map layer surviving a failed activation — or the second service extension with registering consumers.
- **Asset hierarchy.** Nothing decides whether a gimbal is an asset, a component of one, or both. An id's composition inside a source is the adapter's choice, so a future `partOf` field or nested components stay additive rather than breaking. _Trigger to revisit:_ the first capability granted per component rather than per vehicle. ([ADR-0011](decisions/ADR-0011-asset-vocabulary-and-registry.md))
- **Per-property provenance.** The registry records which source asserted an asset, not which source asserted each property. _Trigger to revisit:_ the first property two sources can both assert. ([ADR-0011](decisions/ADR-0011-asset-vocabulary-and-registry.md))
- **The `unknown` overload.** `unknown` currently means both "the adapter saw something gcscode cannot name" and, in practice, "the vocabulary is too coarse for what it saw". _Trigger to revisit:_ the second airframe family that lands in `unknown` for the coarseness reason rather than the genuinely-unnameable one — `HELICOPTER` is the first. ([ADR-0011](decisions/ADR-0011-asset-vocabulary-and-registry.md))
- **Durable identity across reconnect.** Wire ids are reassignable addresses, so a vehicle returning with a different id is a different asset and anything a live-state port associated with the old one is orphaned. _Trigger to revisit:_ the first feature that must recognise the same airframe across a reconnect. ([ADR-0011](decisions/ADR-0011-asset-vocabulary-and-registry.md))
- **Live state — what an asset is _doing_, as against what it _is_.** Position, mode and battery stay on `SitlExports.telemetry`, read directly by three consumers across the protocol boundary. _Trigger to revisit:_ already scheduled as the next iteration — see the roadmap's adapter-neutral live-state entry. ([ADR-0011](decisions/ADR-0011-asset-vocabulary-and-registry.md))
- **First-party-only vocabulary widening.** The asset vocabulary grows on demonstrated first-party need, not on standards coverage: MAVLink and STANAG 4586 are held to two-source expressibility, and neither one's enum is mirrored inward. _Trigger to revisit:_ a third-party extension needing a word gcscode does not have. ([ADR-0011](decisions/ADR-0011-asset-vocabulary-and-registry.md))
- **A change event on the registry.** Consumers observe through reactive reads; there is no `onDidChangeAssets`. _Trigger to revisit:_ the first consumer outside a reactive context, or the first cross-realm consumer — Svelte reactivity does not cross a worker or iframe boundary, so the webview wing fires this. ([ADR-0011](decisions/ADR-0011-asset-vocabulary-and-registry.md))
- **Indexed queries.** `getAssets()` returns everything and consumers filter; there is no query API and no index. _Trigger to revisit:_ an asset count where linear scans in a render path cost measurably. ([ADR-0011](decisions/ADR-0011-asset-vocabulary-and-registry.md))
- **A lint rule for the anti-corruption boundary.** Nothing mechanically stops a protocol identifier leaking inward past an adapter. The reachable half is enum values and message names, excluding package names, URLs and prose; the value half (a bare `2` meaning `MAV_TYPE_QUADROTOR`) is acknowledged as out of a lint rule's reach. _Trigger to revisit:_ the second adapter, where protocol identifiers could leak inward from two directions. ([ADR-0011](decisions/ADR-0011-asset-vocabulary-and-registry.md))
- **Asset liveness.** Nothing times out a vehicle that stopped transmitting; an entry means present-as-asserted-by-its-source, and a source that goes quiet leaves its assets listed until the source itself is disposed. _Trigger to revisit:_ the first operator-visible stale entry, which one link cannot produce. ([ADR-0011](decisions/ADR-0011-asset-vocabulary-and-registry.md), [`specs/2026-10-21-asset-abstraction-v0.md`](specs/2026-10-21-asset-abstraction-v0.md))
- **Distinguishing assets from non-assets.** The MAVLink adapter registers every system that sends a heartbeat, so the operator's own tooling — a GCS, an antenna tracker — is listed as an asset alongside the vehicle. The vocabulary can say such a thing does not fly (`{ kind: 'none' }`) but not that it is not an asset. _Trigger to revisit:_ the first capability that must distinguish non-flying assets from each other. ([`specs/2026-10-21-asset-abstraction-v0.md`](specs/2026-10-21-asset-abstraction-v0.md))

## Tooling / process

- **Contributor-facing docs site.** No Storybook, no docs website. Per-package `README.md` is the contract.
- **Changelog / release tooling.** Nothing is published.
- **CI configuration.** Add when there is something to protect besides a local clean install + tests + lint.
- **Patterns ledger for architecture notes.** No cumulative `docs/patterns.md` ledger and no "Patterns" section in the spec template. Architecture notes (per [`specs/2026-10-15-architecture-notes.md`](specs/2026-10-15-architecture-notes.md)) name established patterns, but nothing tracks which ones gcscode actually applies. Trigger to revisit: the third architecture note that names a pattern applied in gcscode code, not only discussed.

## Agentic team architecture deferrals

These deferrals stem from `docs/specs/2026-05-12-reviews-as-artifacts.md` and the broader agentic-team-architecture arc. Each is a deliberate "we are not building this yet" decision, not just a per-iteration scope cut.

- **Linear integration.** Work-tracking outside GitHub is deferred. The agentic-team workflow uses GitHub state only. Trigger to revisit: gcscode iterations start spawning enough tickets that GitHub Issues alone is painful.
- **Webhook routers / event-driven dispatch.** Beyond the narrow auto-merge GitHub Action (its own follow-up iteration), there is no off-session event handling. Trigger: user wants agents to react to events while no Claude session is live.
- **Multi-model heterogeneous reviewers.** Tried on red-team from 2026-05-16 (per `docs/specs/2026-05-16-multi-model-red-team-v1.md`) and dropped on 2026-10-22: the October review-process evaluation found the Sonnet dispatch added little that Opus had not already raised, so every role is now single-model ([`docs/specs/2026-10-22-review-loop-v2.md`](specs/2026-10-22-review-loop-v2.md)). Trigger to revisit: a later evaluation shows a role's unique findings depend on the model rather than the lens.
- **Effort-level control in reviewer dispatch — partially resolved 2026-05-16.** Red-team and extension-architect run at `effort: max` via `.claude/agents/<name>.md` frontmatter (per [`docs/specs/2026-05-16-effort-max-custom-reviewers.md`](specs/2026-05-16-effort-max-custom-reviewers.md)). The original deferral's rationale — "needs a custom Anthropic API dispatcher" — is **invalidated**, not just superseded: agent-file frontmatter does the job without new infrastructure. **Remaining out of scope:** effort control on feature-PR reviewers (spec-compliance, code-quality, final cross-cutting), which are dispatched by `superpowers:subagent-driven-development` and not under our control. Trigger to revisit the remainder: a dedicated iteration that forks or replaces the superpowers dispatch.
- **Override semantics for agentic reviewers.** No formal "reviewer supersedes ADR" patterns (`blocked-on-adr` labels, counter-proposal ADR PRs). Trigger: a reviewer actually wants to block an iteration on architectural disagreement.
- **Plan-PR workflow.** Plans continue to land on master directly. Specs and ADRs now ship via PR per the red-team-reviewer iteration (`docs/specs/2026-05-14-red-team-reviewer.md`). Trigger to bring plans into PR-workflow: a plan-level reviewer is added.
- **Red-team blocking verdicts + override mechanism.** Red-team still posts `--comment` only, but since review-loop-v2 its `Blocking: N` trailer holds spec/ADR auto-merge shut while blocking findings remain (Gate 3b), which covers most of what verdict promotion was for. Still deferred: a GitHub-native `--request-changes` verdict and a designed override path for intentional drift vs broken premise (today the owner simply merges by hand). Trigger: v2 brainstorm of the verdict-promotion iteration.
- **Automated enforcement of reviewer auto-dispatch.** Dispatching red-team (and, when routed, the extension architect) on spec/ADR PRs is convention-based — the controller must follow the `review-loop` skill (`.claude/skills/review-loop/SKILL.md`). Since review-loop-v2, Gate 3b fails closed when red-team has not reviewed, so a skipped dispatch can no longer auto-merge; nothing makes the dispatch happen. Trigger to revisit: the first spec/ADR PR merged after 2026-10-22 whose timeline lacks a red-team review of its last `Code-review-followup:` commit (PR #38 RT-5). **Precedent (PR #30, 2026-10-15):** the controller skipped the reviewer re-dispatch after two `Code-review-followup:` commits, and #30 merged with its last followup (`0cf8af2`) unreviewed — the trigger's signature, but before the window it counts from (PR #38 RT-16). It was a controller lapse against an explicit obligation, not a gap in the convention's text.
- **Final spec-cross-cutting reviewer with `--approve` power on spec/ADR PRs.** No reviewer on spec/ADR PRs posts an approving verdict; red-team and extension-architect post `--comment` with a `Blocking: N` trailer that Gate 3b reads, and the owner's merge or `auto-merge` label remains the authorization. Trigger: future iteration designing approval-by-bot for specs (likely bundled with the verdict-promotion iteration for red-team and the extension architect).
- **CI integration in auto-merge.** `.github/workflows/auto-merge.yml` doesn't wait on any status check; no CI exists yet. Trigger to revisit: when CI lands, the workflow grows a `needs:` clause (or pre-merge wait-for-checks step) that requires CI green before merging.
- **Branch protection rules.** No GitHub-native branch protection on master. Auto-merge is workflow-convention-only. Trigger: first observed bypass of the workflow's intent (e.g., merge happens without the label and the user regrets it), OR landing GitHub's native auto-merge button (which would require branch protection on the target ref).
- **Agent file discovery hot-reload — still session-bound in practice.** The Claude Code docs say edited `.claude/agents/*.md` files apply on the next dispatch, but on 2.1.309 a session started in `shell/` kept the session-start content of the git-root `red-team-reviewer.md` after git replaced the file and after an in-place change (probes 2026-10-25, PR #39), and a worktree's `.claude/agents/` is not seen at all (probe 2026-10-24). The text below is the original deferral. `.claude/agents/*.md` files are loaded into the Agent tool's `subagent_type` registry at session start only. Creating a new agent file mid-session does not make it discoverable in that session; a fresh session is required. **Observed evidence:** PR #11 (effort-max) and PR #12 (review-discussion-loop-v1) both were bitten by this — the dispatching session in each case fell back to `subagent_type: general-purpose` because the new agent files weren't discoverable. Fixing this would require Claude Code's harness to watch `.claude/agents/` and re-load the registry, which is a harness-level behavior outside gcscode's scope. Trigger to revisit: the harness gains hot-reload behavior, OR a future iteration finds the session-restart workaround painful enough to warrant a workaround (e.g., always create new agent files in a separate session before opening the spec-PR). The workaround pattern (`subagent_type: general-purpose` fallback with full prompt inline) is functionally adequate even when the harness behavior doesn't change.
- **Automated enforcement of "repo-relative paths only" in reviewer output.** Committed docs are checked by `pnpm lint:docs` since review-loop-v2; PR comments are not. v1 of the rule (per [`docs/specs/2026-05-17-relative-paths-in-reviewer-output.md`](specs/2026-05-17-relative-paths-in-reviewer-output.md)) is convention-only — no workflow gate, pre-commit hook, or per-post scan enforces it. Manual discipline (controller scans reviewer output before applying the `auto-merge` label) is the v1 mechanism. Trigger to revisit: the leak-recurrence tripwire fires (any reviewer posts an absolute path that isn't a code-block-flagged-as-leak per the carve-out).
- **Broader leak-class enforcement (beyond filesystem paths).** Out of scope for v1. Future leak classes (env-var values, hostnames, IP addresses, other local-context identifiers) would each need their own rule + enforcement design. Trigger to revisit: a different leak class is observed in reviewer output.
- **Scope extension of "repo-relative paths" to non-PR-posting subagents.** The rule applies only to reviewer subagents (the ones that write to GitHub PR comments). Implementer subagents (e.g., from `superpowers:subagent-driven-development`) and other non-PR-posting subagents are out of scope because their output is local-only and doesn't surface publicly. Trigger to revisit: implementer subagents start posting to PRs OR another subagent class begins producing public artifacts.
- **Verdict promotion for Extension architect** (`--request-changes` blocking power). Extension architect posts `--comment` only, like red-team; since review-loop-v2 its `Blocking: N` trailer holds spec/ADR auto-merge shut when it has reviewed. Trigger to revisit: advisory mandate proves insufficient (a blocking-concern is repeatedly ignored across multiple PRs).
- **Additional domain experts beyond extension architecture** (frontend, security, performance, etc.). v1 ships only the Extension architect. Trigger to revisit: a domain other than extension architecture surfaces enough recurring concerns to warrant a dedicated reviewer role.
- **Automated heuristic enforcement** for routing (workflow-side check). v1 ships convention-only routing — the controller applies the heuristic per the `review-loop` skill; no workflow gate enforces. Trigger to revisit: convention-only enforcement produces recurring routing misses across N=3 PRs.
- **Review freshness in Gate 3b.** The gate reads the latest red-team (and architect) review's `Blocking: N`, not whether that review saw the PR's head commit. What keeps an unreviewed trailing commit out is procedural: the PR stays a draft until the loop's last review, and the pre-gate refuses drafts ([`docs/specs/2026-10-22-review-loop-v2.md`](specs/2026-10-22-review-loop-v2.md) Known unknowns). A `commit_id == head` check would enforce it, at the cost of failing closed on any trailing commit. Trigger to revisit: the first spec/ADR PR, merged after 2026-10-22, whose head commit is newer than its last reviewer review (PR #38 RT-1, RT-5).

## Why this list exists

Agents are biased toward completeness and "one more thing". Without a canonical deferral list, any of the above gets preemptively scaffolded on the first sighting of a near-by commit. This file answers "should I add X?" with a durable "not yet — and here's where it goes when it's time."
