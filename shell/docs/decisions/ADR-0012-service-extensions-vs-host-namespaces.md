# ADR-0012: Domain concerns are service extensions; platform concerns are host namespaces

**Date:** 2026-10-16
**Status:** Accepted

## Context

[ADR-0006](ADR-0006-extensionhost-namespacing.md) made `ExtensionHost` topic-namespaced — `host.commands.*`, `host.window.*`, `host.keybindings.*`, `host.extensions.*` — and said future cross-cutting capabilities land as new namespaces. The fifth namespace, `host.configuration.*`, came later from [`docs/specs/2026-05-18-configuration-system-v1.md`](../specs/2026-05-18-configuration-system-v1.md); ADR-0006 forecast it under a different name (`host.settings.*`). `CLAUDE.md`'s boundary-rule corollary says the same thing in operational form: if an extension needs a capability the host does not expose, add it to `@gcscode/extension-api` first — as a method on an existing namespace, as a new namespace if the capability is cross-cutting, or as a new field on `ExtensionContext`.

That guidance is right for platform capabilities and incomplete for domain capabilities. `@gcscode/extension-map` already took the other path: it exposes `MapApi.registerLayer` and `MapApi.registerControl` through its `activate()` return value, consumed by `extension-flight-overlay` via `host.extensions.getExtension('gcscode.map')?.exports` and a type-only import ([ADR-0005](ADR-0005-extension-boundaries.md)).

To be precise about what is missing, since the pattern itself is not undocumented: [`docs/vs-code-alignment.md`](../vs-code-alignment.md) carries an Alignments row for "Service-style extension exposing contribution surface for other extensions" with `gcscode.map` + `registerLayer` as the gcscode side, and [`docs/roadmap.md`](../roadmap.md) calls Map the "first service-style extension" and says flight-overlay "validates the service-style extension pattern". So the category exists, has a name, and was claimed as deliberate. What was never written down is the **discriminator** — which capabilities belong in that category and which belong on the host — and [`docs/specs/2026-05-03-map-and-flight-overlay.md`](../specs/2026-05-03-map-and-flight-overlay.md) never discusses `host.map.*` as an option at all, so for that iteration the choice really was made in passing.

The asset abstraction forces the discriminator into the open: should the asset registry be `host.assets.*` or an extension exporting an `AssetsApi`? The ports that follow — an adapter-neutral live-state contract, video, commands to assets — each ask it again. Without a stated rule the host wins by default, because a namespace needs no new package, no `getExtension` call, and no undefined handling at the call site. The honest counter-evidence is that the one time this has actually fired since `extension-map` — configuration v1 — went to the host without any re-litigation, and went there correctly. The problem is not that the project keeps arguing; it is that the next call has nothing to cite, and the convenient answer is load-bearing by default.

**Terminology.** This ADR adopts **service extension** as the term of art and treats the earlier "service-style extension" wording in the roadmap and the alignment ledger as referring to the same pattern; those files adopt the shorter term on next touch.

## Decision

**Platform concerns are host namespaces. Domain concerns are service extensions.**

A **platform concern** is a capability about _being an extension host_: registering contributions, executing commands, keybindings, looking up extensions, configuration — and, when they land, events, themes, i18n, per-extension storage. It lands as a method on an existing `host.*` namespace, as a new namespace per ADR-0006, or as a new field on `ExtensionContext` where the capability is per-extension-scoped rather than shared. (That third branch is `CLAUDE.md`'s and it matters: per-extension storage is VS Code's `ExtensionContext.globalState`, not a `vscode.storage.*` namespace that would need an extension id passed in.)

A **domain concern** is a capability about _what gcscode controls or displays_: maps, assets, live state, video. It ships as a **service extension**: its own package, exporting its vocabulary types and its API.

### The test

**Would the host have to own the surface this capability mutates?** If yes, it is a platform concern. That is the whole test.

The counterfactual in "would have to" is load-bearing. Asked in the present tense — _does_ the host own it — the test can only confirm capabilities that already shipped: at the moment configuration was proposed, the host owned no schema registry and no persisted store, so a present-tense reading would have classified it as a domain concern and sent it to an extension. The question is whether the capability's surface must belong to the host for the capability to work at all.

Run backwards over everything shipped, it returns platform for each: `commands` (a registry the palette and the keybinding dispatcher both read has to be the host's; an extension holding it would be the host for that purpose), `window` (the host renders the view and status-bar surfaces, so it must own them), `keybindings` (one dispatcher over one keyboard), `extensions` (the registry and activation lifecycle are the host's definition), `configuration` (schema registration and persistence must be arbitrated in one place across all extensions — true before the namespace existed, which is the point of the counterfactual). A future `events` namespace is platform for the same reason: a bus every extension publishes to and subscribes from cannot belong to one of them. An asset registry is not: nothing in `packages/shell/` renders, persists, or arbitrates asset descriptions, and nothing would have to.

**Replaceability is a smell, not a test.** "Could a third party plausibly ship a competing implementation?" reads as a tempting second test and it is unreliable: it answers _yes_ for configuration (a `localStorage`-backed store needs no host privileges), for an event bus (a `SvelteMap` and some closures), for i18n (a string table), and for per-extension storage — all of which this ADR classifies as platform, correctly, on the ownership test. Use it as a hint when ownership is genuinely unclear, never as a tiebreaker against ownership. If a capability's classification is still unclear after the ownership test, the iteration's spec records the call and its reasoning. Note which way the evidence runs: the ownership test is _derived_ over the five shipped namespaces plus `events`, where there is something to check it against; for i18n, themes and per-extension storage it is _asserted_, and each lands when its own iteration does.

### Mechanics

The mechanics are the existing ones, with one correction to how they are usually described.

- Vocabulary types and the API interface live in the service extension's package; consumers reach them with `import type` from the sibling package, per ADR-0005 and the ESLint `allowTypeImports` carve-out.
- The live API is the `activate()` return value, looked up with `host.extensions.getExtension<T>(id)?.exports`.
- **A service extension exports types from its package entry point, not its live registry.** The singleton stays module-internal and is reachable only through `activate()`'s return value. The rule targets **live state**: a registry, a store, a `$state` proxy. Type-only exports are the point of it, and a published constant is not caught by it — `packages/extension-map`'s `MAPLIBRE_CONTEXT_KEY` is a runtime value that consumers deliberately re-declare rather than import (`docs/out-of-scope.md` carries that as its own deferral), so it stays. `packages/extension-map/src/index.ts` currently also exports `mapApi` itself, which lets shell-side code import a domain registry directly — the boundary lint rule covers `packages/extension-*` only, so `packages/shell/**` may runtime-import any extension package and be lint-clean. That is a change of two export sites in one file in map — the `export { MAPLIBRE_CONTEXT_KEY, mapApi }` statement and any in-tree import the lint follow-up turns up — plus a follow-up on the lint config. Small, but not the one-liner an earlier draft of this ADR called it.
- **Lookup differs by direction, and only the read direction can be lazy.** Readers resolve per use and skip when the service is absent (`extension-flight-overlay/src/state.ts` and `extension-vehicle-status`'s `getSitlExports()` both do this). Registrants cannot: `registerLayer` / `registerControl` are one-shot writes whose `Disposable` belongs to the registering extension's `subscriptions`, so they resolve during `activate()` and depend on `bundledExtensions` order. `extension-flight-overlay/src/index.ts` resolves eagerly and **throws** when map is inactive — deliberately, and tested. An adapter registering assets is register-shaped but driven by inbound protocol traffic, so it can resolve lazily per message and self-heal — subject to ADR-0011's source-claim rules, since a re-resolving adapter must re-claim its source and a claim on a live id throws. A registrant with nothing to wait for cannot resolve lazily at all. Note the seam that creates: a handle or export cached at `activate()` can outlive the service's teardown, so a lazily-resolving registrant must re-resolve rather than trust a cached reference — [ADR-0011](ADR-0011-asset-vocabulary-and-registry.md) states what a stale asset-source handle does (it goes inert), and each service owes the same statement.

  The prescription for a registrant that cannot defer: resolve at `activate()`, and **degrade** — skip the registration, log once, and let the contribution be absent rather than failing activation. Throwing is reserved for a consumer whose entire purpose is that registration, and only once activation-failure containment has landed, which turns the throw into a recorded failed-to-activate rather than a black screen. Until then, flight-overlay's existing throw is the known exception, not the pattern to copy.

- **Service state surviving enable/disable is bounded, not general.** A module-level singleton that outlives the extension is right for registration tables whose disposables are consumer-owned — `mapApi`'s layers and camera, where re-enabling remounts and re-renders. It is not obviously right for a registry of facts _other_ extensions asserted: disabling and re-enabling the service would resurrect descriptions whose asserting adapter may have since disconnected. Each service documents its own re-enable semantics. ADR-0011 gives the asset registry's: nothing survives the registry extension's teardown — sources are disposed, the registry empties, held handles go inert — because resurrecting assets whose asserting adapter is gone is worse than starting empty. A service whose state is consumer-owned registrations (map's layers) may keep `mapApi`'s posture; a service holding facts other extensions asserted should not.
- **Service→service dependencies are permitted**, and ADR-0011's first application creates one: `extension-sitl` becomes an adapter that registers into the assets service while remaining a producer its own consumers read. That is the first two-level chain, and hand-maintained insertion-order comments in `bundled-extensions.ts` become a hand-maintained topological sort as such chains accumulate. The trigger needs stating precisely, because v0 does not fire it: ADR-0011's adapter resolves the assets service lazily per inbound message, so the chain creates no activation-time edge and insertion order remains a comment rather than a constraint. **The trigger is the first service→service edge that must resolve during `activate()`** — which replaces the [`docs/out-of-scope.md`](../out-of-scope.md) row's current "first ordering bug" wording for this case, and is sharper than it: an ordering bug is the symptom, an activate-time edge is the condition that produces it.
- **Adapters are domain concerns too.** An adapter exports no contract — it writes into a port — but it carries protocol knowledge and belongs outside the host for the same reason a map does.
- **The built-in tier is platform-only.** There are three privilege tiers in the tree, not two: host namespaces, the workbench built-in (constructed with the internal `Registry` in `packages/shell/src/main.ts`), and bundled extensions with host access only. A domain capability does not belong in the built-in tier, however convenient registry-level reach would be.

## Consequences

**Positive.**

- **The host stays domain-agnostic in its API.** Nothing in `host.*` knows what a drone is, what an airframe is, or that assets exist, and its surface grows only when platform capabilities grow. (Enforcement is one-directional today — see Known limitations.)
- **Domain capabilities are removable, and swappable while everything is in-tree.** A map not wanted in a build is simply not bundled. That is weaker than "replaceable": the lookup key is a hard-coded extension id, `extension-manager` rejects duplicate ids, and the contract types live inside the incumbent's package — so substituting an implementation means editing the id in every consumer or shipping under the incumbent's id, and a consumer cannot be agnostic about which implementation is present. If a genuine second implementation ever matters, the contract moves to a neutral home (a types-only package, or `extension-api` for contracts with no host implementation) and the lookup becomes contract-keyed. _Trigger:_ the first contract with two plausible providers.
- **First-party features are forced through the public seam.** `extension-assets` gets no privileges `extension-map` lacks, which is what makes "first-party features use the API third parties use" true in practice rather than aspirationally.
- **It retro-justifies `extension-map`, with one qualification.** Map is a domain extension that _also_ registers host contributions for its own UI (`host.window.registerView`) and hosts a contribution surface of its own (`registerControl`, whose clicks route through `host.commands.executeCommand`). "Mutates nothing the host owns" is a claim about the capability a service _exposes_, not a claim that a service never touches host surfaces. Map is a worked example of the distinction, not a frictionless fit.

**Negative.**

- **A missing service is a boot halt today, not an ergonomic tax.** `packages/shell/src/extension-host/registry.ts` calls `extension.activate(context)` with no `try`/`catch`, `extension-manager` propagates, and `main.ts` runs that loop before `mount` — so an operator who disables Map and reloads gets no app, no palette, and no extensions panel to re-enable Map from. A throw mid-`activate` also orphans whatever that extension already registered, because the subscriptions entry is never recorded. This ADR does not create that hole, but it multiplies it: the hazard count grows as consumers × services, and this rule says most product value is a service. **Host-side activation-failure containment is therefore a prerequisite** — contain the throw, record the extension as failed-to-activate, keep booting, surface it in the extensions panel — and it ships as its own iteration before the asset abstraction v0 iteration.
- **Service extensions pay an ergonomic tax on top of that.** `getExtension` plus undefined handling at every call site, against a namespace that is simply always there, and ordering carried in comments rather than declarations.
- **The host's contribution ledger stops being a complete picture, and we accept that.** `registry.listViews()` cannot know that flight-overlay mounted four layers and a control through `mapApi`. The consequences are real and acknowledged: the extensions panel cannot fully answer "what does this extension contribute", an operator cannot shed one misbehaving overlay without disabling its owner, and a future permission or attribution model would need per-service introspection to attach to. _Trigger to revisit:_ the first operator need to disable one contribution without disabling its owning extension.
- **A mis-drawn line costs a migration.** A domain capability that turns out to be universal (selection state is the likeliest candidate — [`docs/roadmap.md`](../roadmap.md) defers it under the Map entry) would move from extension to host, breaking its consumers. Cheap while everything is in-tree per ADR-0005, expensive once extensions ship independently.
- **The line is still a judgment call at the margin.** Unit and formatting preferences, and coordinate-system conversion, are each arguably either. _Trigger to revisit this ADR's test:_ two consecutive iterations whose specs have to record an ambiguous call.

**VS Code alignment.** Aligned in spirit: `vscode.*` is platform, and VS Code's Git extension publishes its API through `getExtension('vscode.git').exports.getAPI(1)` rather than a `vscode.git` namespace. Two divergences to name rather than inherit silently. First, `getAPI(1)` _is_ a version broker — the mechanism that makes the precedent robust — and gcscode defers versioning entirely (ADR-0005), so gcscode's version of this pattern is the precedent minus its versioning layer. Second, VS Code's dominant pattern for domain-ish concerns is the opposite shape: host-owned registries that extensions register providers into (`languages.register*Provider`, `debug.*`, `scm.createSourceControl`, `tasks.registerTaskProvider`), which is how [`docs/architecture/2026-10-15-ports-and-adapters.md`](../architecture/2026-10-15-ports-and-adapters.md) characterizes VS Code's adapter role. gcscode diverges because its domain is the thing extensions contribute, not the product itself — see the first row of Alternatives considered. The existing alignment-ledger row for this pattern cites hover providers as the VS Code side, which is that host-owned shape rather than this one; amending that row is a follow-up.

## Known limitations

- **Enforcement is one-directional.** The restricted-imports rule in `eslint.config.ts` is scoped to `packages/extension-*`, so `packages/shell/**` can runtime-import any extension package — and service extensions that export their live singleton make that trivially easy. "The host stays domain-agnostic" is therefore a convention on the host side. _Trigger:_ fixed by the ESLint-and-`mapApi` follow-up below (one bullet, two edits); until then, treat it as unenforced.
- **No capability or permission scoping.** Any extension can look up any service extension's exports, and exports may include mutable `$state`. Same posture as ADR-0005. _Trigger:_ the untrusted-extension iteration.
- **No dependency declaration, and no versioning of a service's contract.** Ordering is insertion-order convention; the API type is an unversioned contract shared through `workspace:*`. _Trigger:_ the service→service chain named in Mechanics, which ADR-0011's first application creates.
- **Granularity is not decided**, and its costs scale per _service_, not per capability: one more activation edge, one more lookup site, one more ordering comment. The steer, consistent with that: prefer fewer, coarser service extensions, all else equal. _Trigger:_ the asset iteration, which must choose whether the live-state port shares `extension-assets` or gets its own package.
- **Re-enable semantics of a disabled service are undefined** in general and left to each service's spec (see Mechanics).

## Alternatives considered

- **A host-owned _neutral_ registry whose content comes entirely from extensions** — `host.assets.registerAsset(...)` / `host.assets.getAssets()`, with the vocabulary in a **types-only contract package** rather than `@gcscode/extension-api`, and the host holding a collection it has no domain opinions about. Stated at its strongest, because the obvious objection has an answer: putting the types in their own package means the platform package never defines what an airframe is, so "the host would learn the domain" is not the reason this loses. It is the strongest alternative and the closest to VS Code's dominant pattern (`languages.register*Provider`, `debug.*`, `scm.createSourceControl`, `tasks.registerTaskProvider`), it is always available — no `getExtension`, no undefined, no bundle-order dependency, none of the boot-halt hazard above — and the neutral contract home is what would make replaceability real.

  Two reasons it still loses, neither of which a types-only package fixes. First, **the host would own the registry's behaviour, not just its storage**: membership, removal, and what happens when two adapters assert the same asset are domain arbitration, and they would sit in `packages/shell/` where domain rules are hardest to change and impossible to leave out of a build. Second, **it reopens the default this ADR exists to close**: once one domain capability has a host namespace, the next one's cheapest path is another, and the argument for each is identical. The trade accepted: lookup ceremony and an ordering hazard in exchange for a host whose surface stays bounded by what being a host requires. _Reopen with the types-only package as the starting point if:_ activation-failure containment proves insufficient, or a second domain vocabulary wants host-side arbitration.

- **Everything on the host** (`host.assets.*`, `host.map.*` and the rest, domain types included). Rejected: unbounded host surface, un-removable capabilities, and it contradicts the goal of first-party features using the same API as third-party ones. Note this differs from the row above only in whether the host's registries stay domain-neutral.
- **Everything as extensions, platform concerns included.** Rejected as incoherent: the host owns the surfaces contributions mutate, so `registerView` cannot live anywhere else.
- **Case-by-case, no rule.** Rejected: that is today's state, and it leaves the next call with nothing to cite while the convenient answer stays the default.
- **A contract-keyed service locator on the host** (`host.services.get('assets')`). Rejected for now as ceremony — `getExtension` already locates services, and a locator adds a well-known-name registry plus a who-wins policy for a world with one provider per contract. Noted honestly: this indirection is exactly what would separate contract identity from provider identity, so rejecting it is why the "replaceable" claim above is downgraded to "removable, and swappable while everything is in-tree". _Trigger:_ the first contract with two plausible providers.
- **A `contributes`-style declarative service registry.** Rejected: declarative contribution manifests are deferred at the architecture level (ADR-0003, ADR-0007), and nothing here needs static parseability.

## Follow-ups

- **`CLAUDE.md`'s boundary-rule corollary is amended** to carry both paths: platform capabilities go to `@gcscode/extension-api` (namespace method, new namespace, or `ExtensionContext` field); domain capabilities ship as service extensions. That file is the instruction an agent actually executes, so leaving it unamended would keep the host as the documented default — the exact dynamic this ADR exists to end. `packages/extension-api/README.md` gains the same split under its cross-extension-exports section, which today documents the mechanism without saying when to choose it.
- **Host-side activation-failure containment ships as its own iteration, before the asset abstraction v0 iteration** (see Consequences > Negative). Scope: contain the `activate` throw, record failed-to-activate state, keep booting, surface the failure in the extensions panel, and dispose or account for partial registrations.
- **[`docs/vs-code-alignment.md`](../vs-code-alignment.md)**: amend the existing "Service-style extension exposing contribution surface" row to cite this ADR as the rule behind the instance, and correct its VS Code column (hover providers are host-owned registries, which is the divergence named above, not this alignment). Add a Divergences row for the deferred version broker (`getAPI(1)`).
- **[`docs/roadmap.md`](../roadmap.md)** gains the entries both ADRs assume: the asset abstraction v0 iteration, the activation-containment iteration, and the adapter-neutral live-state contract. None appear there today, while the committed `extension-sitl` → `extension-mavlink` rename already refers to "after v0".
- **ESLint and `mapApi`** (one follow-up, two edits): extend the restricted-imports rule to `packages/shell/**` with `bundled-extensions.ts` allowlisted, and stop `packages/extension-map/src/index.ts` exporting `mapApi`.
- **`bundled-extensions.ts` ordering comments**: the `vehicle-status` comment cites ADR-0005's activation-order consequence for a dependency that is now a lazy read, so it overstates the constraint it documents. Correct it when the assets-before-adapter comment lands with the v0 iteration, so the file's ordering rationale matches the read/register split this ADR states.
- ADR-0011's asset registry lands as the service extension `@gcscode/extension-assets` per this rule; the asset abstraction v0 spec cites both ADRs and owns the [`docs/out-of-scope.md`](../out-of-scope.md) propagation for the deferrals above.
