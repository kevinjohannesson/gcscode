# ADR-0018: Vehicle classes are add-ons the MAVLink extension selects per vehicle

**Date:** 2026-11-24
**Status:** Proposed

## Context

The steady core gcscode is working towards flies one to five vehicles, by mission, by hand, or both: a vehicle flies its waypoints, holds, is flown by hand for a task, and is handed back to fly home. The core's v0 is copter-only. Later classes (fixed-wing, VTOL, ground vehicles) must not mean a rewrite, and copter assumptions must not leak into parts that every class shares.

Most of what the core hardens does not depend on the class: the link, live state and its freshness, the command lifecycle, alert machinery, the map, video, mission upload and per-vehicle identity. A short list of questions does:

- **The safe hold, and what taking over means.** A copter holds in Loiter; a plane cannot hover and circles; a VTOL's answer depends on whether it is hovering or in forward flight; a ground vehicle stops. Centred throttle is a hover for a copter, a cruise speed for a plane and a stop for a rover.
- **Which modes pass the pilot's stick straight through**, so a feature can warn or refuse before entering one. Malloy T150 went from RTL into Stabilize at 2.6% throttle (HF §1.1, §5 row 2).
- **Which commands cannot be undone** (HF §5 row 6). How force is expressed is not a class question: MAVLink defines it (`MAV_CMD_COMPONENT_ARM_DISARM` with param2 21196).
- **What a failsafe does**, so the lost-link behaviour can be shown (HF §5 row 13).
- **Mode names and numbers**, which differ per firmware: ArduCopter's mode 5 is Loiter, ArduPlane's is FBWA.

The human factors report proposes the same split: the core asks each firmware extension to declare these answers (HF §6, "Ask each firmware extension to declare"). Today one answer is hardcoded in the wrong place: `extension-mavlink`'s telemetry store holds ArduCopter's mode names, so a plane's modes would show with a copter's names. The roadmap's N13 plans more of the same, "a per-firmware table the MAVLink extension keeps".

Three things are already decided. [ADR-0014](ADR-0014-protocols-as-languages.md) Decision 2: each feature owns its contract, protocols fill it in, a feature asks about one asset key at a time and only that key's source answers; there is no gcscode-wide dictionary of vehicle facts. Its Decision 3: an add-on built on one protocol's extension carries the protocol's name and may read its exports. Its Decision 4: `extension-assets` keeps identity only. [ADR-0016](ADR-0016-one-station-process.md): only the MAVLink extension's station process sends to vehicles.

VS Code solves the same shape for programming languages. The editor holds no TypeScript or Python core. Each feature is a provider API, such as `languages.registerHoverProvider(selector, provider)`, and a `DocumentSelector` (usually a `languageId`) picks which providers answer for a document. Facts that need no code go in a declarative language configuration (`languages.setLanguageConfiguration`: comments, brackets). If no provider matches, the feature is not offered for that document. A new language is one more extension, and the core does not change.

## Decision

1. **One core; behaviour that depends on the firmware lives only in vehicle class add-ons.** No generic feature, and not the MAVLink extension itself, decides from a vehicle's class, firmware or mode numbers how it flies, which mode a number means, or what a command does to it. Facts MAVLink itself defines, read straight off a field, stay with the MAVLink extension and need no class: the airframe from HEARTBEAT `type`, the armed state from `base_mode`, force disarm, the mode number. A class is one registration, and one add-on may make several: `extension-mavlink-ardupilot` is the first add-on, and it registers the ArduPilot copter class now and the plane and rover classes when they come, as one VS Code extension serves both TypeScript and JavaScript. The cost is that classes are enabled per autopilot, not per class.
2. **Each feature owns the class questions it needs, in its own contract** (ADR-0014 Decision 2). Manual control asks for the safe takeover mode, the RTL mode and how sticks map, commands ask which are irreversible, the mode display asks for names and which modes pass raw stick, missions ask how to resume. The questions are written without a class in mind: "the mode to hold in", never "Loiter".
3. **The MAVLink extension stays the source that answers, and selects a class per vehicle.** Its exports gain `registerVehicleClass(selector, vehicleClass)`, returning a `Disposable`. The selector names the HEARTBEAT fields that identify a class in MAVLink's own enum names, as mavlink2rest delivers them: `{ autopilot: 'MAV_AUTOPILOT_ARDUPILOTMEGA', types: ['MAV_TYPE_QUADROTOR', 'MAV_TYPE_HEXAROTOR', …] }`. It is matched against the HEARTBEAT of the vehicle's autopilot component only, the one whose `autopilot` is not `MAV_AUTOPILOT_INVALID`, as the vehicle status contract's Goal 3 reads its inputs; a gimbal, camera or companion computer heartbeating under the same system id never changes the match, and a system that has never sent an autopilot HEARTBEAT (another ground station, an ADS-B receiver) is not asked class questions at all. Selection is live: it is redone on each autopilot HEARTBEAT and each registration or disposal, so a feature that holds a live answer sees a class that registers after it asked. The MAVLink extension calls each class inside a guard of its own: a class that throws answers "unavailable" for its own vehicles, logged once, and never hides another class's vehicles or the class-neutral facts.
4. **A heartbeat selects a candidate; the firmware confirms it.** HEARTBEAT `type` is what the firmware chooses to report, and ArduPlane with QuadPlane reports its `Q_MAV_TYPE` parameter, which an owner may set to `MAV_TYPE_QUADROTOR`. So a class also names, as data, what confirms the firmware it serves from something no parameter changes (for ArduPilot copters, for example, the name `ArduCopter` in the firmware's version banner), and its answers apply only once that is confirmed; until then the vehicle's class questions are unavailable. The evidence is asked for by the station process, the only sender (ADR-0016 Decision 1): once for each autopilot it newly hears and again after its own restart (ArduPilot sends its banner on request, such as `MAV_CMD_DO_SEND_BANNER`, not on a schedule). The process keeps the answer and hands it to the page in each `hello`, so a page that loads after the vehicle booted is not left without it. The exact request and evidence are for N14's spec.
5. **No confirmed match, no answer.** A vehicle that no class matches, or whose firmware is not yet confirmed, gets "unavailable" for every class question, never a guess. Each feature decides what "unavailable" means for it: a feature with a conservative answer uses it (the mode display shows the mode number, as the vehicle status contract already does for a vehicle with no mode table; a command is confirmed as if it were irreversible), and a feature with none turns off for that vehicle and says so ("no vehicle class for ArduPlane fixed-wing: manual takeover unavailable"). Everything class-neutral (link, position, alerts from the vehicle's own text, missions shown) still works.
6. **Two classes never match one vehicle: an overlapping registration is refused.** Selectors are finite lists, so `registerVehicleClass` can tell when a new selector overlaps a live one (same autopilot, a type in common, the same firmware) and throws, as `createSource` and `registerStatusProvider` refuse a second claim. The operator sees it as that add-on's failed activation. This means enabling an add-on can never take a class away from a vehicle already flying under another; the cost is that the order in which add-ons activate picks which one is refused.
7. **Answers that a station job uses are data, handed to the station process.** Manual control runs in the station process, and the page is never on the path of its loop ([ADR-0015](ADR-0015-native-sidecars.md) Decision 2, ADR-0016 Decision 4). So every class answer the station needs (the takeover and RTL modes, how sticks map, which modes pass raw stick) is declarative data, like VS Code's language configuration, and the MAVLink extension's page half hands it to its process for each vehicle once that vehicle's class is confirmed (Decision 4), again whenever it changes, and again for every vehicle on each `hello` from the process, so a restarted station is configured without a page reload; this is the "configures them" of ADR-0015 Decision 2. The process refuses a takeover for a vehicle it holds no confirmed class data for. A class may answer with a function only for a question asked in the page. What the process keeps of that data while the page reloads joins ADR-0016's open question of what the process keeps sending while no page reaches it, and two tabs that each hand class data for the same vehicle, the last one winning, join its open question of what happens when two pages connect.
8. **A class add-on sends nothing.** Only the station process sends (ADR-0016 Decision 1).
9. **v0 ships one class, ArduPilot copters.** ArduCopter's mode names move out of the MAVLink extension's telemetry store into `extension-mavlink-ardupilot` (the roadmap's N14). That step also adds an ArduRover or ArduPlane SITL build to `tools/sitl`, which builds ArduCopter only today, and adds a smoke test that runs that vehicle through the class-neutral parts and checks that its class-specific features show as unavailable rather than wrong. The reference sortie (fly the mission, hold, take over by hand, hand back, fly home) is written into [`docs/smoke-tests.md`](../smoke-tests.md) in class-neutral steps by the last step it exercises, manual control's hand-back in N13.
10. **A class is done when the reference sortie passes on its own SITL frame.**

## Consequences

- Adding a class is one registration in an add-on, and no change to the core or the MAVLink extension while the existing class questions cover it. The first non-copter class will not be that cheap: questions written with only copters in view will be copter-shaped, and that class will revise some contracts. The non-copter SITL of Decision 9 catches some of this, not all. Work grows as classes × features, as protocols × features already does under ADR-0014.
- One class object answers every feature's questions for its vehicles, so a vehicle's mode names and its takeover mode cannot disagree. The reverse cost: each new class question changes the MAVLink extension's class type and every class add-on.
- A mixed station (copters and a rover on one screen) needs nothing extra: each vehicle is matched on its own autopilot heartbeat.
- The roadmap changes. N14, the ArduPilot add-on and the class registry, is placed in M3, after N1's station work (the station asks for the firmware evidence) and before the first step that needs a class answer: M3's mode changes, M4's lost-link display (what a failsafe does) and N13's mode table all wait for it, and none hardcodes a copter answer in the meantime. Until N14 ships, ArduCopter's mode names stay in the MAVLink extension's telemetry store, as the vehicle status contract's Goal 3 has them today; N14 removes that one hardcoded answer. The first manual control step that changes a vehicle's mode (taking over, handing back) waits for N14; steps that only read the radio do not.
- A vehicle has no class until its first autopilot heartbeat and its confirmed firmware, and changes class if its autopilot heartbeat does (a VTOL reports the same type in both phases, so its phase is a question for the class, and a phase-dependent answer the station needs is a table keyed by a field the station hears, not a function). A class add-on that is disabled mid-flight makes its vehicles' class features unavailable at once; whether a feature in use, such as manual control, ends or holds when that happens is for the feature's spec.
- A class add-on registers in `activate()`, which makes it the first extension besides the flight overlay to register into another extension's registry there and fires the trigger of the [`docs/out-of-scope.md`](../out-of-scope.md#extension-machinery) row "Cleanup of contributions an extension registered into another extension's registry". Whether class registrations survive the MAVLink extension's own disable and re-enable is the re-enable posture ADR-0012 leaves to each service. Both are settled by the spec of the step that builds the class registry (N14), before it ships (PR #108 RT-11, PR #108 EA-3).
- Copter, plane and rover share one ArduPilot add-on (Decision 1), so their shared code needs no library and no runtime import between add-ons ([ADR-0005](ADR-0005-extension-boundaries.md)).
- PX4 is the same pattern with `autopilot: 'MAV_AUTOPILOT_PX4'`, in a PX4 add-on. Another protocol would bring its own source and its own class registry, as ADR-0014 expects.
- The name "vehicle class" is chosen over "profile", which `libs/radio-input` already uses for a radio's input mapping.
- VS Code alignment. Aligns: providers chosen by a selector, a declarative configuration beside code, a disposable registration, and a feature not offered when nothing matches. Aligns too: when two providers could answer where only one answer can apply, VS Code formats nothing until the user picks a default formatter, and gcscode does not guess either; it diverges in how the conflict is settled, by refusing the second registration rather than asking the operator. Diverges, new ([ledger](../vs-code-alignment.md#divergences) "Who selects a vehicle's class"): the registry belongs to the source extension, not the host or a feature, because the selector reads protocol fields only the source sees, and it holds one object per class that answers every feature, the shape of QGroundControl's firmware plugin rather than VS Code's one registry per feature.
