# ADR-0019: The station takes a system ID only when told one, and without one it sends nothing

**Date:** 2026-11-25
**Status:** Proposed

## Context

[ADR-0016](ADR-0016-one-station-process.md) gives gcscode one station process with one MAVLink identity: one system ID and one heartbeat, addressed to no vehicle, for every vehicle (its Decision 3). It leaves open, for the step that first sends a heartbeat (GCS-30), which system ID that is and what a watch-only station does with its heartbeat. The roadmap's N1 asks for both, plus a configurable system ID and a watch-only setting as the MAVLink extension's own work ([`docs/roadmap.md`](../roadmap.md#m3--first-commands-bound-and-guarded)). [ADR-0018](ADR-0018-vehicle-classes-as-selectors.md#consequences) adds one question for N1's watch-only: whether a watch-only station still asks each autopilot for the evidence that confirms its firmware (PR #108 RT-20).

What a vehicle does with a ground station's system ID, read from ArduPilot's master branch, which `tools/sitl/setup.sh` clones (`libraries/GCS_MAVLink/GCS.cpp` and `GCS_Common.cpp`, `ArduCopter/events.cpp`):

- `MAV_GCS_SYSID` (default 255; earlier releases call it `SYSID_MYGCS`) and `MAV_GCS_SYSID_HI` (default 0) name the system IDs the vehicle treats as its ground station: one ID, or the range between them when `_HI` is the larger. `GCS::sysid_is_gcs` is the only test.
- The GCS failsafe's "last seen" time is fed by three messages from such an ID, and only these: `HEARTBEAT`, `RC_CHANNELS_OVERRIDE` and `MANUAL_CONTROL`. Commands, mode changes and requests feed nothing. The heartbeat's `type` and `autopilot` are not checked: any HEARTBEAT from ID 255 counts.
- `RC_CHANNELS_OVERRIDE` and `MANUAL_CONTROL` from any other ID are dropped. Commands are accepted from every ID, unless the owner sets `MAV_OPTIONS` bit 0, which drops everything from IDs outside the GCS range.
- Copter's GCS failsafe never fires on a vehicle that has never seen its GCS. Once it has, it fires after `FS_GCS_TIMEOUT` without one of those three messages, when `FS_GCS_ENABLE` is on (off by default).

What already speaks to the dev stack's vehicles, and as whom:

- **MAVProxy**, one per vehicle (`tools/sitl/run_sitl.sh`), uses its default source system 255 and heartbeats at 1 Hz.
- **mavlink2rest 1.0.2**, which the page reads telemetry from, defaults to system 255, component 0, and heartbeats every second as `MAV_TYPE_ONBOARD_CONTROLLER` (its `src/cli.rs` and `src/mavlink_vehicle.rs`). MAVProxy forwards that heartbeat to the vehicle.
- **The SITL Python client** (`pnpm fly-sitl`, `tools/sitl/client/mav_helpers.py`) sends as 255. It sends commands, mode changes, stream requests and position targets, but no heartbeat and no overrides.

So today every dev-stack vehicle already hears two "ground stations" on 255, neither of which is gcscode, and with `FS_GCS_ENABLE` on, its GCS failsafe could never fire while mavlink2rest runs. A station heartbeat on 255 would add nothing a vehicle or the wire probe could tell apart, and GCS-30's done line, "when the process stops, the heartbeat stops and each vehicle's own failsafe applies", could not be shown.

Watch-only is the same failure seen from the field. A second screen that heartbeats on a vehicle's GCS ID keeps that vehicle's GCS failsafe from firing after the station that controls it is lost (PR #61 RT-14). The roadmap names two answers: stop heartbeating, or heartbeat on an ID outside the vehicle's GCS IDs. ADR-0016 Decision 3 already rules out the per-vehicle form, since one heartbeat reaches every vehicle on the link.

## Decision

1. **The station's system ID is given to the station process when it starts**, with `--system-id <1–255>`, and stays fixed while it runs. It is the process's, not a page's: two tabs see one station (ADR-0016 Decision 3), so the ID cannot be a setting each page hands over. ID 0, MAVLink's broadcast, and anything outside 1–255 is refused with one line saying why, as a bad `--profile` is. Changing the ID, or moving between watch-only and sending, is a restart of the process.
2. **Without a system ID, the station is watch-only, and a watch-only station sends nothing to any vehicle**: no heartbeat, no control frame, no command and no request. It still reads the radio and serves the page. This is the default, so no station ever asserts itself to a vehicle unless someone chose the identity it asserts. Watch-only is station-wide; watching one vehicle while controlling another is not built (Consequences).
3. **The station never writes a vehicle's GCS IDs.** It does not set `MAV_GCS_SYSID`, `MAV_GCS_SYSID_HI` or `MAV_OPTIONS`. Making a vehicle accept a station is the owner's setup, like binding a radio, because those parameters are stored on the vehicle and change what every other station's controls do. The station's ID is chosen to match the vehicle, not the other way round.
4. **The dev stack gives the station 255**, which every unconfigured ArduPilot vehicle accepts, **and nothing else in the dev stack uses 255.** MAVProxy moves to source system 250 (`--source-system 250`), mavlink2rest to system 251 (`--system-id 251`) and the SITL Python client to 252. They keep their own heartbeats, which feed no failsafe on those IDs, and the wire probe and a vehicle can tell each of them from the station. With the station stopped, no dev-stack vehicle hears a ground station at all.
5. **The station's heartbeat says it is a ground station**: component `MAV_COMP_ID_MISSIONPLANNER` (190, MAVLink's component for a GCS), `type` `MAV_TYPE_GCS`, `autopilot` `MAV_AUTOPILOT_INVALID`, `base_mode` and `custom_mode` 0, `system_status` `MAV_STATE_ACTIVE`. With `autopilot` invalid, the MAVLink extension's asset adapter and ADR-0018's class selection never take the station for a vehicle.
6. **The page is told which the station is.** The station's `hello` carries its system ID, or says it is watch-only, and the MAVLink extension's Link state view shows it beside `station: running`. The field, and the protocol version it raises, are GCS-30's.
7. **A watch-only station does not ask for firmware evidence** (ADR-0018 Decision 4, PR #108 RT-20). It sends nothing, Decision 2 here, so its vehicles' classes stay unconfirmed and their modes show as numbers (ADR-0018 Decision 5).

## Consequences

- GCS-30 (the station heartbeat) builds Decisions 1, 2, 4, 5 and 6: the `--system-id` flag, the heartbeat, the three dev-stack ID changes in `tools/sitl`, the `hello` field and its line in the Link state view, and the README updates for the station, SITL and the wire probe. Its proof gains a step it could not have before: stop the station and the wire probe shows no heartbeat from 255 while MAVProxy's (250) and mavlink2rest's (251) go on. Until GCS-30 ships, the dev stack is unchanged and still heartbeats on 255 from MAVProxy and mavlink2rest.
- A vehicle set up for another station's ID does not hear gcscode's control until the owner changes `MAV_GCS_SYSID` on the vehicle or starts the station with that vehicle's ID. That is the cost of Decision 3. The gain is that gcscode never changes stored settings another station relies on.
- With the dev-stack IDs moved, MAVProxy's own `rc` command no longer overrides a vehicle's sticks, since 250 is not a GCS ID; its mode and arm commands still work. The SITL client's commands work as before, since ArduPilot accepts commands from any ID unless `MAV_OPTIONS` bit 0 is set, and their `COMMAND_ACK`s go to 252, not to the station, so GCS-48 (the first command) never sees answers to commands it did not send.
- An operator who gives the station 255 beside another ground station on 255, such as QGroundControl or Mission Planner with their defaults, has two senders on one GCS ID, and either one keeps the vehicle's GCS failsafe from firing when the other is lost. The station cannot see the other one unless the link routes its heartbeat back, and telling that from an echo of its own heartbeat is unproven. Detecting a second sender on the station's ID is left open, with the trigger that a rung first runs gcscode beside another ground station, or that GCS-30's proof shows the station's link hears other GCS heartbeats.
- Watch-only is per station, not per vehicle. A station that controls vehicle 1 and only watches vehicle 2 would need vehicle 2's GCS IDs to exclude the station's ID, which the station cannot check without reading parameters. Per-vehicle watch-only is not built; its trigger is the first rung that controls one vehicle while another is flown from a different station.
- Switching watch-only from the page is not built either: Decision 1 makes it a restart. The roadmap's N1 "watch-only setting" is this start-up choice until a rung needs to switch while flying, and that rung decides what switching does to manual control or a command in progress. If operators switch it in normal use, it fires the "Settings editor UI" row of [`docs/out-of-scope.md`](../out-of-scope.md#extension-machinery), as N1 already says.
- A watch-only station shows every vehicle's mode as a number (Decision 7). That is the cost of sending nothing at all: an allow-list of "harmless" requests would need its own proof that each one changes nothing for any other station, and a request still needs a source ID that some vehicle may count as its GCS once `MAV_OPTIONS` bit 0 is set. Revisit when an operator needs mode names while watching, for example the first rung that adds a second, watching station.
- Still open from ADR-0016's Consequences, and not decided here: when the heartbeat and manual control stop and what the process keeps across a reload, how the page names a vehicle to the process, and what happens when two pages connect. Decision 1 narrows the last one only for the identity: two pages can never give the station two IDs.
- PX4 vehicles are not checked here. `tools/sitl` builds ArduCopter only, and PX4's rule for which heartbeats count as its ground station is not read off its source in this ADR. The first PX4 rung checks it against Decisions 2 and 4.
- VS Code has no counterpart: a vehicle's ground station identity has no equivalent in an editor. Nothing goes into [`docs/vs-code-alignment.md`](../vs-code-alignment.md).
