# ADR-0019: The station takes a system ID only when told one, and without one it sends nothing

**Date:** 2026-11-25
**Status:** Proposed

## Context

[ADR-0016](ADR-0016-one-station-process.md) gives gcscode one station process with one MAVLink identity: one system ID and one heartbeat, addressed to no vehicle, for every vehicle (its Decision 3). It leaves open, for the step that first sends a heartbeat (GCS-30), which system ID that is and what a watch-only station does with its heartbeat. The roadmap's N1 asks for both, plus a configurable system ID and a watch-only setting as the MAVLink extension's own work ([`docs/roadmap.md`](../roadmap.md#m3--first-commands-bound-and-guarded)). [ADR-0018](ADR-0018-vehicle-classes-as-selectors.md#consequences) adds one question for N1's watch-only: whether a watch-only station still asks each autopilot for the evidence that confirms its firmware (PR #108 RT-20).

What a vehicle does with a ground station's system ID, read from ArduPilot's master branch, which `tools/sitl/setup.sh` clones (`libraries/GCS_MAVLink/GCS.cpp` and `GCS_Common.cpp`, `ArduCopter/events.cpp`):

- `MAV_GCS_SYSID` (default 255) and `MAV_GCS_SYSID_HI` (default 0) name the system IDs the vehicle treats as its ground station: one ID, or the range between them when `_HI` is the larger. `GCS::sysid_is_gcs` is the only test. Released Copter 4.6 has `SYSID_MYGCS` in place of `MAV_GCS_SYSID`, `SYSID_ENFORCE` in place of `MAV_OPTIONS` bit 0, and no `_HI` range.
- The GCS failsafe's "last seen" time is fed by three messages from such an ID, and only these: `HEARTBEAT`, `RC_CHANNELS_OVERRIDE` and `MANUAL_CONTROL`. Commands, mode changes and requests feed nothing. The heartbeat's `type` and `autopilot` are not checked: any HEARTBEAT from ID 255 counts.
- `RC_CHANNELS_OVERRIDE` and `MANUAL_CONTROL` from any other ID are dropped. Commands are accepted from every ID, unless the owner sets `MAV_OPTIONS` bit 0, which drops everything from IDs outside the GCS range.
- Copter's GCS failsafe never fires on a vehicle that has never seen its GCS. Once it has, it fires after `FS_GCS_TIMEOUT` without one of those three messages, when `FS_GCS_ENABLE` is on (off by default, and off in SITL's `copter.parm`).

What already speaks to the dev stack's vehicles, and as whom:

- **MAVProxy**, one per vehicle (`tools/sitl/run_sitl.sh`), uses its default source system 255 and heartbeats at 1 Hz on its vehicle link.
- **mavlink2rest 1.0.2**, which the page reads telemetry from, defaults to system 255, component 0, and heartbeats every second as `MAV_TYPE_ONBOARD_CONTROLLER`, with no option to stop it (its `src/cli.rs` and `src/mavlink_vehicle.rs`). It listens with `udpin`, so each heartbeat goes back only to the MAVProxy it last heard from, which forwards it to that one vehicle.
- **The SITL Python client** (`pnpm fly-sitl`, `tools/sitl/client/mav_helpers.py`) sends as 255. It sends commands, mode changes, stream requests and position targets, but no heartbeat and no overrides.

So today every dev-stack vehicle already hears its MAVProxy heartbeat on 255, and with `FS_GCS_ENABLE` on, its GCS failsafe could never fire while MAVProxy runs. A station heartbeat on 255 would add nothing a vehicle could tell apart, and GCS-30's done line, "when the process stops, the heartbeat stops and each vehicle's own failsafe applies", could not be shown.

Watch-only is the same failure seen from the field. A second screen that heartbeats on a vehicle's GCS ID keeps that vehicle's GCS failsafe from firing after the station that controls it is lost (PR #61 RT-14). The roadmap names two answers: stop heartbeating, or heartbeat on an ID outside the vehicle's GCS IDs. ADR-0016 Decision 3 already rules out the per-vehicle form, since one heartbeat reaches every vehicle on the link.

## Decision

1. **The station's system ID is given to the station process when it starts**, with `--system-id <1–255>`, and its identity (an ID, or none) stays fixed while it runs: changing it is a restart. It is the process's, not a page's: two tabs see one station (ADR-0016 Decision 3), so the ID cannot be a setting each page hands over. ID 0, MAVLink's broadcast, and anything outside 1–255 is refused with one line saying why, as a bad `--profile` is. The ID to give is the one the vehicles' `MAV_GCS_SYSID` names. Whether a station with an ID heartbeats for its whole run, or only while the MAVLink extension holds a session to it, is not decided here: it is ADR-0016's open question of when the heartbeat stops, and GCS-30's.
2. **Without a system ID, the station is watch-only, and a watch-only station sends nothing to any vehicle**: no heartbeat, no control frame, no command and no request. It still reads the radio and serves the page, and refuses, with an answer saying it is watch-only, any send a connection asks of it. This is the default, so no station ever asserts itself to a vehicle unless someone chose the identity it asserts. Watch-only is station-wide; watching one vehicle while controlling another is not built (Consequences).
3. **The station never writes a vehicle's GCS IDs on its own initiative.** It does not set `MAV_GCS_SYSID`, `MAV_GCS_SYSID_HI` or `MAV_OPTIONS` (in Copter 4.6, `SYSID_MYGCS` and `SYSID_ENFORCE`). Making a vehicle accept a station is the owner's setup, like binding a radio, because those parameters are stored on the vehicle and change what every other station's controls do. Whether a parameter write the owner asks for, such as N6's parameter copy across vehicles, may touch them is N6's to decide.
4. **The dev stack gives the station 255**, which every unconfigured ArduPilot vehicle accepts, **and nothing else in the dev stack uses 255.** MAVProxy moves to source system 250 (`--source-system 250`), mavlink2rest to system 251 (`--system-id 251`) and the SITL Python client to 252. They keep their own heartbeats, which feed no failsafe on those IDs. With the station stopped, no dev-stack vehicle hears a ground station at all.
5. **The station's heartbeat says it is a ground station**: component `MAV_COMP_ID_MISSIONPLANNER` (190, MAVLink's component for a GCS), `type` `MAV_TYPE_GCS`, `autopilot` `MAV_AUTOPILOT_INVALID`, `base_mode` and `custom_mode` 0, `system_status` `MAV_STATE_ACTIVE`. The page does not tell a GCS heartbeat from a vehicle's today: `extension-mavlink`'s asset adapter makes an asset of every system that heartbeats, and its telemetry store takes `armed` and `mode` from every HEARTBEAT. So the station's heartbeat must not reach the page's mavlink2rest feed until the page takes mode and armed only from autopilot heartbeats (the roadmap's "Vehicle status owns its contract"). GCS-30's link is built to that constraint, or brings that page change with it. The station showing as an asset once its heartbeat does reach the page is the accepted cost of the "Distinguishing assets from non-assets" row in [`docs/out-of-scope.md`](../out-of-scope.md#extension-machinery), as for any GCS.
6. **A station that hears an autopilot HEARTBEAT (`autopilot` not `MAV_AUTOPILOT_INVALID`) under its own system ID sends nothing while it does**, and tells the page why, so the Link state view shows the station stopped rather than its ID as if it were sending. The message is GCS-30's. ArduPilot takes everything from its own system ID as one of its own components, so a station given a vehicle's ID would speak as part of that vehicle.
7. **The page is told which the station is.** The station's `hello` carries its system ID, or says it is watch-only. The MAVLink extension is the one reader of it on the page, as it is of `stationProtocol`: its Link state view shows it beside `station: running`, its exports carry it, and the contracts it fills answer "unavailable: watch-only" for anything that would send (ADR-0014 Decision 2), so no other extension offers a control that does nothing. GCS-30 builds the `hello` field, the protocol version it raises and the Link state line. The station's refusal and the "unavailable: watch-only" answers come with the first step that adds a send a page or another extension can ask for (GCS-48's command, N13's takeover), which is also the station's first act on what a connection sends and so settles ADR-0015 Decision 4's check of who is connecting; the export comes with its first reader.
8. **A watch-only station does not ask for firmware evidence** (ADR-0018 Decision 4, PR #108 RT-20). It sends nothing (Decision 2). Whether evidence heard without asking, such as a banner another station's request brings, confirms a class is for N14's spec; the costs below hold unless it does.

## Consequences

- GCS-30 (the station heartbeat) builds Decisions 1 to 6 and Decision 7's `hello` field and Link state line: the `--system-id` flag, the heartbeat, the three dev-stack ID changes in `tools/sitl`, and the README updates for the station, SITL and the wire probe, whose `to system 255` and "as system 255" lines Decision 4 makes false. The ID changes ride with the heartbeat rather than a rung of their own: alone they show only a loss (MAVProxy's `rc` stops overriding), and GCS-30's done line needs both at once. GCS-30 also updates `docs/smoke-tests.md` § Station in the dev stack, whose goal "it sends nothing to any vehicle" stops being true once the dev stack starts the station with 255. Until GCS-30 ships, the dev stack is unchanged.
- GCS-30's done line is shown on the vehicle, not the wire probe. The probe listens on a MAVProxy output, which carries what the vehicle sends and never MAVProxy's own heartbeat or another output's traffic, so it cannot see 250, 251 or a station behind MAVProxy. With `FS_GCS_ENABLE` on for that run only, from a copy of SITL's `copter.parm` passed as `SITL_DEFAULTS` (a `param set` would be saved in each vehicle's `eeprom.bin`, which `tools/sitl/run_sitl.sh` keeps between runs), freezing the station makes each vehicle that heard it announce its GCS failsafe after `FS_GCS_TIMEOUT`; freezing, because a station that exits stops the whole dev stack ([`docs/specs/2026-11-24-station-in-dev-stack.md`](../specs/2026-11-24-station-in-dev-stack.md)). The ticket's other proof, the heartbeat at 1 Hz with no gap over 1.5 s on the wire probe, needs a path to the probe that GCS-30 adds, for example the station sending a copy of each heartbeat to the probe's port; or the ticket's "how you'll see it" changes.
- GCS-30's link must reach every vehicle with one heartbeat (ADR-0016 Decision 3). A link that listens with `udpin` as mavlink2rest does answers only the last sender, and with several vehicles would reach one of them.
- A vehicle set up for another station's ID does not hear gcscode's control until the owner changes its `MAV_GCS_SYSID` or starts the station with the ID it names. That is the cost of Decision 3. The gain is that gcscode never changes on its own a stored setting another station relies on.
- With the dev-stack IDs moved, the SITL client's commands work as before, since ArduPilot accepts commands from any ID unless `MAV_OPTIONS` bit 0 is set. Their `COMMAND_ACK`s are addressed to 252 but still reach every MAVProxy output, so GCS-48 (the first command) matches each answer's `target_system` to the station's ID.
- Watch-only covers the station, not the bridge. Until telemetry moves into the station (ADR-0016 Decision 5), mavlink2rest heartbeats on its own, as 255 unless told otherwise, so a setup is watch-only only if mavlink2rest also runs on an ID outside every vehicle's GCS IDs. Decision 4 does that in the dev stack; the step that first runs gcscode outside the dev stack does it there.
- An operator who gives the station 255 beside another ground station on 255, such as QGroundControl or Mission Planner with their defaults, has two senders on one GCS ID, and either one keeps the vehicle's GCS failsafe from firing when the other is lost. Those two also default to component 190, so they share the station's exact address, and ArduPilot does not forward a heartbeat to a link that has sent the same system and component: the vehicle never passes the other station's heartbeat on, and the station cannot detect it that way. Detecting a second sender on the station's ID is not built; its trigger is the first rung that runs gcscode beside another ground station, which also decides whether the station needs a component of its own.
- Watch-only is per station, not per vehicle. A station that controls vehicle 1 and only watches vehicle 2 would need vehicle 2's GCS IDs to exclude the station's ID, which the station cannot check without reading parameters. Per-vehicle watch-only is not built; its trigger is the first rung that controls one vehicle while another is flown from a different station.
- Changing the ID or watch-only from the page is not built either: Decision 1 makes it a restart, and the roadmap's N1 "configurable system ID" and "watch-only setting" are start flags of the MAVLink extension's native half, not `host.configuration` settings. Its trigger is how an operator's machine starts the station ([ADR-0015](ADR-0015-native-sidecars.md) Decision 7), or the first rung that needs to switch while flying, which decides what switching does to manual control or a command in progress.
- Unless N14's spec counts evidence heard without asking (Decision 8), a watch-only station gets no class answer for any vehicle (ADR-0018 Decision 5): modes show as numbers, and every class feature, M4's lost-link display included, is unavailable. That is the cost of sending nothing at all: an allow-list of "harmless" requests would need its own proof that each one changes nothing for any other station, and a request still needs a source ID that a vehicle may refuse once `MAV_OPTIONS` bit 0 is set. Revisit when a watching station needs any class answer, for example the first rung that adds a second, watching station.
- Still open from ADR-0016's Consequences, and not decided here: when the heartbeat and manual control stop and what the process keeps across a reload (Decision 1 leaves it to GCS-30, which likely brings forward ADR-0015 Decision 4's check of who is connecting, since no local program's session may keep a heartbeat alive), how the page names a vehicle to the process, and what happens when two pages connect. Decision 1 narrows the last one only for the identity: two pages can never give the station two IDs.
- Left open when this ADR's review stopped, for the owner:
  - PR #118 RT-17: Decision 5's constraint lifts too early. "Vehicle status owns its contract" fixes mode and armed for vehicle status only and keeps the shared telemetry store as it is for its other readers (the MAVLink view, and the flight overlay's drone icon and heading line until the map contract), so the constraint holds until `applyMessage` takes mode and armed from autopilot heartbeats alone. No planned step makes that change: GCS-30 keeps the station's heartbeat out of the page's mavlink2rest feed, or makes the change itself.
  - PR #118 RT-13: Decision 2's refusal is given to GCS-30 by the first Consequence ("Decisions 1 to 6"), but Decision 7 gives it to the first step that adds a send; Decision 7 is the one meant.
  - PR #118 RT-18: Decision 7's "so settles ADR-0015 Decision 4's check" holds unless GCS-30 has already brought that check forward, as the Consequence on ADR-0016's open questions expects.
- PX4 vehicles are not checked here. `tools/sitl` builds ArduCopter only, and PX4's rule for which heartbeats count as its ground station is not read off its source in this ADR. The first PX4 rung checks it against Decisions 2 and 4.
- VS Code alignment. Diverges, new ([ledger](../vs-code-alignment.md#divergences) "Where a native process's settings live"): VS Code keeps a language server's settings in its extension's settings and hands them to the server; gcscode keeps the station's identity in the process's start flags, shows the page only what it is in `hello`, and changes it by a restart, because one process serves every page.
- `docs/out-of-scope.md` gains the four deferrals above (per-vehicle watch-only, switching from the page, detecting a second sender, class answers while watching), and its "Control authority across stations" row now says watch-only is a start flag.
