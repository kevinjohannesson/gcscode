# ADR-0015: Native processes do the work the browser must never stall

**Date:** 2026-11-22, amended 2026-11-24 to fit [ADR-0016](ADR-0016-one-station-process.md)
**Status:** Accepted

## Context

gcscode is a browser app with no backend: it reaches the vehicle through mavlink2rest, a tool. Manual control is the first feature whose loop must keep time whatever the page is doing. In the browser it cannot: the Gamepad API exists only on the main thread, and the owner's work GCS, which reads its controller there, is unreliable under UI load and in throttled tabs. Chrome slows the timers of a tab hidden for over five minutes to about once a minute. A page also cannot read USB serial ports reliably, start a process, or keep running once it is closed.

VS Code moves the same kind of work out of its UI process: a language server or a debug adapter runs as a separate process, an extension is its client, and the two speak a protocol over a pipe or a socket.

This ADR was first drafted on 2026-11-22 with manual control as a "sidecar" of its own that sent to the vehicle by itself. [ADR-0016](ADR-0016-one-station-process.md), merged since, decides _what_ runs outside the page: one station process, the MAVLink extension's native half, sends everything gcscode sends to vehicles, manual control included. It leaves _how_ a native process is built, packaged, reached and started to this ADR, and names three places where the first draft had to change: its first process, whether the page is on the path of a command, and its trigger for a backend. This version makes those changes. PR #68, still open, builds the first: `packages/mavlink-station`, which reads the radio and serves its raw input to the page.

## Decision

1. **Work that must keep time, or keep going when the page stalls, runs in a native process** that ships as part of gcscode. The station process of ADR-0016 is the first. Whether there is ever a second is ADR-0016's question, not this ADR's: this ADR says only how any native process is built.
2. **Timed loops run inside the process, not in the page.** The page watches and configures them, and a page that stalls, hides or closes never delays a tick. A command the operator gives in the page, such as an arm or a mission upload, does start there and pass through the MAVLink extension to the process (ADR-0016 Decision 2); what the page is never on is the path of a loop that keeps time, such as manual control's frames or the heartbeat.
3. **A native process is one extension's native half**, packaged apart only because it is Rust, as the station is the MAVLink extension's (ADR-0016 Decision 2). That extension owns its address, as one setting under the extension's id, and holds the connection that stands for it: opened in `activate`, with its disposable pushed to `context.subscriptions` as soon as it opens, so that a deactivate and a failed activation both close it, as `extension-mavlink` does with its asset adapter. Whether other page code may connect too is ADR-0016's open question; such a connection never stands for the owner.
4. **The page reaches a native process over a WebSocket on `127.0.0.1`.** The process listens on the loopback address only, and refuses a connection whose `Origin` header is not a page origin it serves, since any website can open a WebSocket to `localhost`. That check filters browsers only. Any program on the machine, from any account or a sandboxed app, can connect and send whatever `Origin` it likes, and an allowed origin such as `http://localhost:5173` names a port, not gcscode's page. This is accepted while a process acts on nothing a connection sends; before one first does, that step decides how the process tells gcscode's page from everything else, for example a per-run secret that only gcscode's dev server hands its page, and how the page trusts what answers on the port. Each process's protocol carries a version in its first message, because it is a contract between two languages; a page that gets a version it does not speak treats the process as unreachable: it says so and sends nothing (ADR-0016 Decision 6).
5. **A native process is written in Rust**: no garbage collector in a timed loop, one binary to ship, and the crates it needs (SDL3 for controllers, `mavlink`, `serialport`) are current. mavlink2rest, already in the dev stack, is Rust too.
6. **A native process lives in `packages/`**, as gcscode's fourth kind of package beside the shell, the extension API and the extensions, with a `package.json` whose `start` runs it and whose `test:rust` runs its tests. The root `pnpm build`, `pnpm test`, `pnpm check` and `pnpm lint` do not take in Rust packages yet, so working on the page needs no Rust; bringing them in is a step of its own on the roadmap. Tools in `tools/` that are written in Rust, such as `radio-probe`, follow the same scripts.
7. **The dev stack starts native processes, and the page never does.** Until a successor to the dev stack's spec adds them to `pnpm dev:sitl`, a process starts with its own `start` script. That spec also settles restarting a process, since the dev stack's spec stops the stack when one service exits and ADR-0016 makes restarting the station part of the step that brings the heartbeat. How an operator's machine starts one is decided when someone other than the owner installs gcscode.

## Consequences

- Building gcscode's native half needs a Rust toolchain and CMake (SDL is built from source), and the repo has a second language that the ESLint boundary rules do not see. A native process never imports TypeScript, and the page sees only its protocol.
- The `Origin` check is a process's only defence against other websites, and it has none against other local programs until the step Decision 4 names.
- A native process is where a timed loop protects itself from its operating system, such as macOS App Nap. Each platform needs its own measures. The station has none yet: the step that first runs a timed loop in it brings macOS's and shows they work.
- Decision 4 answers how the page and a process reach each other and whom the process lets in, which ADR-0016 and the roadmap's N1 left in two places (PR #62 RT-12). How the process tells gcscode's page from other local programs, and how the page trusts what answers, stay open until the step Decision 4 names.
- Which other extensions' page code may connect to the station process, and what enforces it, is ADR-0016's open question (PR #62 RT-5, EA-2). PR #68's Radio input view keeps the station's address in its own setting and connects when the view opens, a read-only connection of that kind; the address moves to the MAVLink extension's setting with the step in which that extension first connects, and the question is settled before any page code sends to the process.
- When a native process becomes a backend is ADR-0016's to set (its Decision 5 and the open PR #62 RT-7), so this ADR sets no trigger of its own.
- Two steps are owed, both on the roadmap: Rust in the root scripts, and the station in `pnpm dev:sitl` through a successor to the dev stack's spec. Until both land, a developer who changes Rust code runs `test:rust` by hand.
- Left open for the owner (PR #75 RT-8): whether a native process may build on a tool's Rust crate, as the station uses `radio-probe`'s radio reading, while `CLAUDE.md` says gcscode reaches `tools/` only over the protocols a real system uses; if not, the shared code moves to `libs/` or into the process.
- VS Code alignment: the process boundary, and one extension owning each process and the session to it (Decision 3), align with language servers. Three things diverge. Who starts the process: a VS Code extension spawns its server and stops it on deactivate, and a gcscode page cannot, so the dev stack does, while the extension still opens and closes its session. The transport: a language server's stdio pipe belongs to the extension that spawned it, while a loopback port is open to every local program (Decision 4). The version: LSP negotiates capabilities in `initialize`, and each side ignores what it does not know, while gcscode's page and process must speak one version. That holds while the dev stack starts both from one checkout, and is revisited when a process is installed or updated apart from the page. What a process keeps doing with no page connected is ADR-0016's open question.
