# One-command dev stack

**Date:** 2026-11-10
**Status:** Draft

`pnpm dev:sitl` starts the simulated world (SITL with MAVProxy and mavlink2rest, MediaMTX, and gcscode's dev server), says when the drone is ready to fly, and one Ctrl-C stops it all. MediaMTX moves into the repo to make that possible.

## Context

Today the owner starts five things by hand: MediaMTX from a downloaded binary, SITL (`pnpm --filter sitl start`), camera-sim, `pnpm dev`, and a Python script to fly the drone, which needs a venv activated first. The [video feed](2026-11-09-video-feed.md) plays WHEP straight from that hand-run MediaMTX.

The design was settled with the owner in the session before this spec. Their decisions, marked _(Owner.)_ below:

1. A native launcher on this Mac now, "something I can run and be done". Docker Compose comes later. The owner's next machine is also a Mac, so Intel and Apple Silicon must both work.
2. MediaMTX comes into the repo as a pinned, checksum-verified download fetched by setup, as `tools/sitl/setup.sh` fetches mavlink2rest, plus a committed config. The hand-run copy retires.
3. The launcher starts SITL with MAVProxy and mavlink2rest, MediaMTX, and gcscode's dev server from the checkout the command runs in.
4. The launcher never moves the drone. Manual control will come later and must not fight a launcher that moves the vehicle. Flying is a separate command with arguments, `pnpm fly-sitl --circle 3`, built in its own PR.
5. A port already in use stops the launch with a message naming the port, and nothing gets killed. The owner often has other instances running.
6. Each service keeps its config in its own `tools/` folder, so a later Compose file can reuse it.

The controller session made four further calls, which the owner saw without objecting; they are marked _(Controller.)_ Choices left to this spec are marked _(My call.)_

## Goals

1. `pnpm dev:sitl`, run from the root of any checkout, starts the three services and prints "ready to fly" once the vehicle can arm.
2. One Ctrl-C stops everything the launcher started, and nothing else.
3. A port already in use stops the launch before anything starts. _(Owner.)_
4. MediaMTX lives in `tools/mediamtx`: a pinned v1.21.3, checksum-verified, plus a committed config. _(Owner.)_
5. Works on Intel and Apple Silicon Macs. _(Owner.)_

## Non-goals

- **Moving the drone.** The launcher never arms, takes off or changes mode; `pnpm fly-sitl` does that. _(Owner.)_
- **Camera-sim.** It joins once a headless test passes; see [its slot](#camera-sims-slot). _(Controller.)_
- **Docker Compose.** It is the eventual follow-up, on the [roadmap](../roadmap.md#tools--considering-not-yet-committed). _(Owner.)_
- **Linux and Windows.** macOS only, like `tools/sitl`.
- **Two stacks at once, several vehicles, or a dev server beside another checkout's.** Every port is fixed, so a second launch stops at the port check, and so does a launch while another checkout's `pnpm dev` holds 5173: stop that one first.
- **Restarting a crashed service.** One service exiting stops the stack.
- **Running setup.** The launcher never downloads or builds anything.
- **Starting a subset.** Each service still starts alone: `pnpm --filter sitl start` (with MAVProxy's prompt), `pnpm --filter mediamtx start`, `pnpm dev`.

## Design

### MediaMTX in the repo (`tools/mediamtx`)

A workspace package like `tools/sitl`, with:

- **`setup.sh`** (`pnpm --filter mediamtx run setup`) installs MediaMTX v1.21.3 into `GCSCODE_MEDIAMTX_HOME`. It picks `darwin_amd64` or `darwin_arm64` by `uname -m`, checks the archive against a sha256 committed in the script (copied from the release's `checksums.sha256`, so the commit, not the download, is the trust anchor), and extracts only the `mediamtx` binary. It skips the download when `mediamtx --version` already prints the pinned version. MediaMTX is MIT-licensed. _(Owner.)_
- **`run.sh`** (`pnpm --filter mediamtx start`) execs that binary with the committed config. Without the binary, it says to run setup and names the command.
- **`mediamtx.yml`**, the config, below.

**`GCSCODE_MEDIAMTX_HOME`** defaults to `~/.gcscode/mediamtx`, beside SITL's `~/.gcscode/sitl`, and must be an absolute path, as `GCSCODE_SITL_HOME` must. It holds only the binary: with the config below MediaMTX writes no files. Not in `GCSCODE_SITL_HOME/bin` because MediaMTX is not part of SITL: camera-sim and, later, real cameras use it without SITL. _(My call.)_

**The config** keeps MediaMTX's defaults, which are what the owner runs today, what camera-sim expects and what the Video panel's default `http://localhost:8889/drone-1/whep` reads, and turns off the servers nothing uses:

```yaml
# Unset keys keep MediaMTX's defaults. camera-sim publishes (WHIP) and the
# Video panel reads (WHEP) over WebRTC on 8889, ICE on UDP 8189; RTSP on 8554
# serves players such as VLC.
rtmp: false
hls: false
srt: false
moq: false
paths:
  all_others:
```

_(My call.)_ Measured on 2026-11-10 with the owner's v1.21.3 binary on spare ports: unset keys keep their defaults (`webrtcAllowOrigins: ['*']`, the stock users); it listens on TCP 8554 and 8889 and UDP 8000, 8001 and 8189; and with MoQ off it writes no `auto.crt` or `auto.key` into its working folder, which the stock config does. `paths: all_others:` must be stated: without it MediaMTX refuses a WHIP publish to `drone-1` with "path 'drone-1' is not configured".

Like the owner's instance today, it listens on all interfaces and lets anyone publish or read. The streams are simulated, and binding to loopback would mean rechecking WebRTC's ICE candidates for no gain on one machine. _Trigger to revisit:_ the first real camera, or running the stack on an untrusted network. _(My call.)_

### The launcher (`scripts/dev-stack.mjs`, `pnpm dev:sitl`)

**Name and place.** The root `package.json` gets `"dev:sitl": "node scripts/dev-stack.mjs"`. `dev:sitl` reads as `pnpm dev` plus SITL, in the root's `<command>:<variant>` style (`lint:docs`, `test:scripts`). The launcher is one file in the root's `scripts/`, beside `lint-docs.mjs`. It is not a `tools/` folder: it starts gcscode itself, which nothing in `tools/` does, and it holds no service config (decision 6 keeps that in each service's folder). The dev server it starts belongs to the checkout the launcher file is in, so each worktree runs its own code. It takes no arguments; the tools' environment overrides (`SITL_MODEL`, `GCSCODE_SITL_HOME`, `GCSCODE_MEDIAMTX_HOME`) pass through. _(My call.)_

**Node, not bash.** Node is already required by pnpm, and a plain `.mjs` with no dependencies needs no build step. It reads mavlink2rest's JSON for the readiness check without `jq` or the venv's Python, binds UDP ports to test them (`nc -z` only tests TCP), prefixes three interleaved output streams and manages process groups in a few lines, and its tests (`scripts/dev-stack.test.mjs`) run under the existing `pnpm test:scripts`. process-compose would do much of this from a YAML file, but it is another pinned download, and the pre-arm check would still need a script. _(My call.)_

**Services.** The launcher keeps them in one table, so camera-sim is one more entry. All three start at once:

| Service    | Started as                                                 | Ports checked first                  | Up when, within                                     |
| ---------- | ---------------------------------------------------------- | ------------------------------------ | --------------------------------------------------- |
| `sitl`     | `tools/sitl/run_sitl.sh --non-interactive --streamrate 25` | TCP 5760, 8088; UDP 14551            | mavlink2rest has a `HEARTBEAT` from vehicle 1, 60 s |
| `mediamtx` | `tools/mediamtx/run.sh`                                    | TCP 8554, 8889; UDP 8000, 8001, 8189 | TCP 8889 accepts, 10 s                              |
| `gcscode`  | the shell's `dev` script with `--port 5173 --strictPort`   | TCP 5173                             | TCP 5173 accepts, 30 s                              |

A service not up by its deadline is a failed launch, handled like a service that exits during startup (see "Setup not run" below). Both flags reach MAVProxy through `run_sitl.sh`'s argument forwarding. `--non-interactive`: the launcher has no terminal to give it, and flying goes through `pnpm fly-sitl`. `--streamrate 25`: MAVProxy's default of 4 Hz moves the map and camera-sim's view in steps, and with no prompt nothing else could raise it; 25 is the rate camera-sim's README and the video feed's demo use. Pinning the dev server to 5173 applies decision 5 to it as well: Vite's habit of moving to the next free port would make the printed URL the only way to tell this checkout's gcscode from another one's, and would put it on 5174, camera-sim's port, once camera-sim joins. The cost is in the Non-goals. _(My call.)_

**Port check.** Before starting anything, the launcher tests every port in the table: TCP by connecting on 127.0.0.1 and ::1, UDP by binding and releasing. Any port in use stops the launch with a message naming the port, the service that needs it and, when `lsof` can tell, the PID holding it. Nothing is started or killed. _(Owner.)_

**Ready to fly.** Once all three are up, the launcher polls mavlink2rest every second until vehicle 1 shows both: `SYS_STATUS`'s `onboard_control_sensors_health` includes `MAV_SYS_STATUS_PREARM_CHECK`, and `EKF_STATUS_REPORT`'s `flags` include `EKF_POS_HORIZ_ABS`. The pre-arm bit alone is not enough. ArduCopter runs its GPS and position checks only when the current mode needs a position, and SITL boots in STABILIZE with `ARMING_NEED_LOC` 0 and no fence, so the bit can turn healthy before there is a position, and `pnpm fly-sitl` would then fail to arm in GUIDED. `EKF_POS_HORIZ_ABS` is the absolute position GUIDED needs (`Copter::ekf_has_absolute_position`). Setting `ARMING_NEED_LOC` would make the bit cover it, but the launcher only watches the vehicle and never configures it. _(Controller: "ready to fly" means the vehicle can arm, GPS and position estimate ready. The signal is my call.)_ It then prints "ready to fly" with the gcscode URL, the MAVLink WebSocket, the WHEP and RTSP addresses, and `pnpm fly-sitl` as the next step. If both are not set after 120 seconds, it says so once, points at MAVProxy's PreArm messages above, and keeps waiting: the stack is still useful without an armable vehicle. _(My call.)_

**Logs.** Each service's stdout and stderr go to the terminal, every line prefixed with its name (`sitl | `), as `docker compose up` shows them. The launcher writes no files of its own; the tools keep the files they write today (SITL and mavlink2rest in `/tmp`, MAVProxy's telemetry logs in `GCSCODE_SITL_HOME/logs`). One terminal to watch, and nothing new to find or clean up. _(My call.)_

**Stopping.** Each service runs in its own process group, so the terminal's Ctrl-C reaches the launcher and not the services. Under `pnpm dev:sitl` it reaches the launcher twice, because pnpm forwards the SIGINT it gets to its script, so signals within a second of the first count as the same Ctrl-C. The launcher then sends SIGTERM to each group by the PID it recorded at spawn (`kill(-pid)`), never by name or pattern, since the owner's own servers have the same command lines. A group still alive after 5 seconds gets SIGKILL; a second Ctrl-C, pressed later than that first second, skips the wait. The launcher PR tests stopping through `pnpm dev:sitl`, not only through `node scripts/dev-stack.mjs`. The same happens on SIGTERM or SIGHUP to the launcher, and when a service exits by itself, which the launcher reports with that service's name before exiting 1. _(Controller: Ctrl-C stops everything by PID. The rest is my call.)_ If the launcher itself is killed with SIGKILL, its services outlive it; the next launch's port check names the ports and the PIDs holding them.

**Setup not run.** The launcher repeats no setup checks. Each start script refuses to start without its setup: `run_sitl.sh` does today, though its message for a missing SITL binary names no setup step and its venv and mavlink2rest messages say `./setup.sh`; the launcher PR makes those three name `pnpm --filter sitl run setup`, and `tools/mediamtx/run.sh` names its command from the start. A service that exits during startup is a failed launch: the launcher stops the others, shows the last lines of every service that exited, and exits 1. _(My call.)_

### Camera-sim's slot

Camera-sim (`tools/camera-sim`, a browser page that publishes WHIP as `drone-<sysid>`) is not in the first launcher. It joins as one table entry, its dev server on 5174 plus a headless Chrome opening the page, once a throwaway test shows that works on this Mac. If a browser cannot run it headless, the owner rethinks the sim. _(Controller.)_ The test is in the [Known unknowns](#known-unknowns).

## Known unknowns

- **Camera-sim headless.** A throwaway test in `scratch/` runs camera-sim in headless Chrome on this Mac and records whether WebGL runs (GPU or software), the frame rate, and whether WHIP publishing holds a stream that the Video panel plays for several minutes. It blocks neither feat PR. If it passes, camera-sim joins the launcher in its own PR; if not, the owner rethinks the sim. _(Controller.)_
- **The ready-to-fly signal from a cold start.** Measured on 2026-11-10 against a running SITL with mavlink2rest 1.0.2: the pre-arm bit and `EKF_POS_HORIZ_ABS` are both set once the vehicle is ready, and mavlink2rest renders both flag fields as names joined by `|`. The launcher PR starts SITL cold, records when each turns on, and checks that `pnpm fly-sitl --circle 3`, run as soon as "ready to fly" prints, arms in GUIDED at the first attempt. The timings also check the 120-second figure.
- **MAVProxy with no terminal.** `--non-interactive` with stdin closed is expected to run cleanly; the launcher PR confirms it.
- **Apple Silicon.** The arm64 path (MediaMTX's `darwin_arm64` archive, mavlink2rest's `aarch64` binary, SITL's native build) is untested until the owner has that machine.
