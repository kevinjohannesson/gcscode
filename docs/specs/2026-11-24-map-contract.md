# The map owns its contract

The map draws one symbol per vehicle, each from that vehicle's own data, through a contract it publishes and protocol extensions fill in. It copies the shape of the [vehicle status contract](2026-11-19-vehicle-status-contract.md), takes over `airframe`, the vehicle symbol and its heading line from the flight overlay, and fixes the rule for who gets a click on the map before anything takes one.

Decisions are marked _(Owner.)_ or _(Controller.)_. The owner set the scope on 2026-11-24 (roadmap M2, the Map lane's GCS-62 and GCS-63) and called the work largely mechanical; every other decision here is _(Controller.)_, taken by the session that wrote this spec, and open to the owner in review. _(Controller, in review.)_ marks one taken on a finding of this spec's review, PR #79, and _(Owner, after review.)_ one the owner took during it.

## Context

The map shows a single drone. `packages/extension-mavlink-flight-overlay/src/layers/drone-icon-layer.svelte` draws one DOM marker from `MavlinkExports.telemetry`, the module-level store in `packages/extension-mavlink/src/telemetry-store.svelte.ts` that every MAVLink system writes into in turn. With `pnpm dev:sitl --vehicles 2` the marker jumps between the two vehicles as their `GLOBAL_POSITION_INT` frames alternate. The Map input view (GCS-14, PR #71) makes this visible: it keeps the same frames apart per system id and names the system whose frame the merged store holds, which is the vehicle the map draws at that moment.

The heading line and the recenter command read the same store. The home marker and the range circle are hardcoded (`packages/extension-mavlink-flight-overlay/src/flight-overlay-config.ts`). The drone icon, the heading line and the home marker are DOM markers, which paint above every canvas layer; the range circle is a style layer. `MapApi` (`packages/extension-map/src/map-api.svelte.ts`) offers layers, controls and the camera, and no input surface.

What is already decided:

- [ADR-0014](../decisions/ADR-0014-protocols-as-languages.md) Decision 2: each feature owns its contract and protocols fill it in, one asset key at a time. Decision 3: "what a generic contract comes to cover moves there, as the overlay's vehicle symbol will once the map draws symbols". Decision 4: `airframe` leaves `extension-assets` "for the map's contract".
- The vehicle status contract spec fixed the provider pattern this contract copies (Approach A, "answer when asked"), MAVLink's per-system state taken only from each system's autopilot component (its Goal 3), and MAVLink's provider clock (its Design).
- Roadmap M2 asks this spec to end the flight overlay's reads of the merged store, take over `airframe`, and decide who gets a click on the map, since N2, N4, N5 and N11 all take clicks.
- The steady core's map criteria, from the owner's "Steady core: definition and acceptance criteria" (kept outside this repo): **P1**, a vehicle marker matches telemetry within one rendered frame of the state change, heading within 2°, measured by a probe on the map's GeoJSON source against live state; **P3**, an item updated by id moves in place; **P6**, a stale vehicle looks stale per **S1**, within 0.5 s of its stream's limit, position 2 s; **P7**, no leaked layers or markers across disable and enable.

## Goals

1. **The map publishes a vehicle symbol contract** as a port of its own service extension ([ADR-0012](../decisions/ADR-0012-service-extensions-vs-host-namespaces.md)): the vocabulary types from `@gcscode/extension-map`'s entry point, and `MapApi.registerSymbolProvider(sourceId, provider)`, returning a `Disposable`. One provider per source id; a second registration on a live id throws, as `registerStatusProvider` and `createSource` do. _(Owner: the map's contract. Shape: Controller, copying vehicle status.)_
2. **A symbol is position, heading, airframe, armed state and when its position arrived.** Position is latitude and longitude. Heading is degrees true, or absent when the vehicle does not report one. Airframe uses the five words `extension-assets` has today (`multirotor`, `fixed-wing`, `vtol`, `none`, `unknown`). Armed is a boolean. The arrival time is when gcscode received the position, on the monotonic clock `performance.now()`, which the contract's doc comment names; the map judges age on the same clock (Goal 6), so a wall-clock step never greys or ungreys every vehicle at once. Altitude, mode, battery and a name are not in it: the map shows none of them, and the contract carries no field that nothing shows. _(Controller. The clock: Controller, in review.)_
3. **The map draws every symbol and its heading line itself,** one per asset whose provider gives a position, from one GeoJSON source in style layers the map owns. Each feature carries its asset key as a property, and the source's `promoteId` names that property: MapLibre's GeoJSON worker reads a string feature `id` as an integer, so `asset-1` would come back as `NaN` (PR #79 RT-7). The GeoJSON source is what P1's probe reads, and the promoted key is what P3 and the click rule need. The symbol's shape follows the airframe; armed keeps today's look (filled green when armed, grey outline when not), and the heading line shows while armed, as today. The map keeps its layers above every other style layer, and moves them back on top whenever another layer is added after them. That is a rule the map can hold over style layers only: a DOM marker paints above the canvas whatever the map does, so the extensions in this repo draw no DOM markers on the map once this spec ships (Goal 5), and the map's README says why. _(Controller, in review: PR #79 EA-1, EA-2, RT-5.)_
4. **MAVLink answers for MAVLink vehicles,** one per system id, from that system's autopilot component only, as the vehicle status contract's Goal 3 takes status: position and heading from its `GLOBAL_POSITION_INT`, airframe from its `HEARTBEAT.type`, armed from its `HEARTBEAT.base_mode`. A `hdg` of `UINT16_MAX` means heading unknown, not 655.35°. Position is absent while `lat` and `lon` are both exactly 0, which is what ArduPilot sends before it has a position (`docs/roadmap.md`, "Camera sim, after v0"), so such a vehicle is not drawn and "Show All Vehicles" does not reach for it (PR #79 RT-1). A system that has never sent an autopilot HEARTBEAT, such as another ground station, has no symbol. _(Controller.)_ The autopilot component's HEARTBEAT state lives in one per-system record, the one vehicle status's first PR gives MAVLink ("MAVLink keeps a status per system id"); whichever of the two first PRs lands first brings it, and the other reads it (PR #79 RT-3). The provider's position and heading also live in that record, parsed from the autopilot component's `GLOBAL_POSITION_INT` only and filtered where they are stored, so another component's frame never replaces the autopilot's (PR #79 RT-3). The Map input view's tracker (`packages/extension-mavlink/src/vehicle-inputs.svelte.ts`) stays GCS-14's proof tool and is not the provider's source (Known unknowns, "The Map input view and GCS-14's rung"). _(Owner, after review: a new rung leaves older proof views alone.)_
5. **The flight overlay stops reading the merged store.** Its drone icon and heading line leave: the map draws both (Goal 3), so they grey and leave together. The home marker and the range circle stay in the overlay, a `mavlink`-named add-on that may read the MAVLink extension's exports (ADR-0014 Decision 3), drawn per vehicle from a per-system export of home positions that the MAVLink extension adds beside `telemetry`. Home comes from each vehicle's `HOME_POSITION`, as the Map input view reads it, instead of the hardcoded `homeLocation`; a vehicle with no home yet has no home marker and no range circle. The home marker becomes a style layer, below the map's symbol layers. _(Controller. The heading line and the home marker's layer: Controller, in review, PR #79 EA-1, EA-2.)_ The cost is that a protocol add-on can no longer restyle the heading line.
6. **A stale symbol looks stale** (GCS-63, P6). A symbol whose position arrived more than 2 s ago, S1's position limit, takes a stale look within 0.5 s of crossing it, and its live look again on the next fresh position. The stale look differs from both the armed and the disarmed look, so a disarmed vehicle that goes quiet changes too (PR #79 RT-2), and the heading line takes it with the symbol. The map runs one clock for this, pushed to its `subscriptions`, since nothing arrives to re-render a vehicle that went quiet. A stale symbol stays drawn where it was last heard: the map never times a vehicle out (`docs/out-of-scope.md`, "Asset liveness"). _(Controller.)_
7. **Recenter moves to the map** with the symbol, as "Map: Show All Vehicles": it fits the camera to every drawn symbol, and with one symbol centres on it at the current zoom. With none, the map's corner notice says there is no vehicle to show, since the palette and map buttons drop a command's result (PR #79 RT-9). Once N2 brings a selection, the selected vehicle is the natural target; that is N2's call. _(Controller.)_
8. **One rule for clicks on the map,** fixed now and built by its first consumer (Click rule). _(Owner: M2 decides it. The rule: Controller.)_

## Non-goals

- **Selection, colour and callsign** (roadmap N2). Symbols carry no name or colour of their own until N2 decides where identity lives. The click rule below leaves selection its place.
- **Building the input surface.** This spec fixes the rule; the first extension that takes a click builds the API (Click rule).
- **Any other map item** (missions, fences, traffic, points of interest), layer ordering beyond the map's own layers on top, and tile failure (GCS-64, P5).
- **Removing `airframe` from `extension-assets`.** Its roadmap entry, "`airframe` leaves `extension-assets`", removes it once the map's contract carries it; this spec only adds it here.
- **The map demo.** `@gcscode/extension-map-demo` still reads the merged store. It is being retired on its own; until then it keeps the mix-up.
- **Video, actions, alerts,** and anything that writes to a vehicle.

## Design

**The contract** sits in `@gcscode/extension-map`'s entry point beside `MapApi`: a `VehicleSymbol` type with Goal 2's fields, a symbol provider type, and `registerSymbolProvider`. A provider is asked once per asset, with that asset's `RegisteredAsset`, and answers with a reactive object that stays current; its symbol is absent while the asset is not a vehicle and appears when it becomes one. The map asks again only for a key new to it or when a source's provider changes, and keeps nothing for a key that has left `getAssets()`, since keys are still reissued. The provider finds its system by `localId`, as vehicle status's provider does. All of this is the vehicle status contract's Design, applied to the map.

**Which vehicles exist** comes from `AssetsApi.getAssets()`, read lazily by the map's view, the read direction ADR-0012 lets resolve per use. An asset whose source has no provider is not drawn: a symbol needs a position, which only a provider has. With the Assets service absent, the map shows a one-line notice in a corner, so an empty map never reads as "no vehicles". _(Controller.)_

**When a provider throws,** the map reads each source's answers inside a guard of its own, draws that source's other vehicles as far as it can, and shows a one-line notice naming the source by the label it registered with, since under [ADR-0011](../decisions/ADR-0011-asset-vocabulary-and-registry.md) a `sourceId` never renders. A throw never breaks the map view. _(Controller.)_

**MAVLink's provider** registers on the provider clock that the vehicle status contract's Design gives the MAVLink extension, not in `activate()`: until it holds a registration, the clock looks up the map's exports on each tick and registers when it finds them. So the map gets its symbols whether it activates at boot, later or after a failed activation, and no activation-time edge forms between the two extensions. The registration sits behind the provider's disposed guard and is owned by the provider, which disposes it with itself. Whichever of this spec's first PR and vehicle status's first PR lands first brings the clock, and with it the edits vehicle status's spec ties to a clock registrant: the ADR-0012 Mechanics breadcrumb, the `packages/extension-api/README.md` rewording, the amended ledger row "Lazy resolution of a service dependency", and the reworded default in the `docs/out-of-scope.md` row "Extension activation ordering / dependency declaration". If this spec's first PR lands first, it also makes vehicle status's first-PR amendments of the `docs/out-of-scope.md` rows "Distinguishing assets from non-assets" and "Service-extension granularity", whose triggers it then fires, naming the map's contract (PR #79 RT-6). The other PR reuses the clock and adds its own provider to that breadcrumb and that ledger row. _(Controller. The edits: Controller, in review, PR #79 EA-8, RT-6.)_

**Across the map's re-enable.** Symbol providers live in the same module-level `mapApi` as layers and controls, which outlives the map's disable and re-enable; re-enabled, the map asks the providers already registered. `MapApi`'s doc comment states that every registration, layers, controls and providers, survives the map's own disable and re-enable, the statement vehicle status's spec asks the map to make (PR #60 EA-17). This spec's first PR makes it, if vehicle status's second PR has not. The map's layers and source are created by the map view on each mount and removed on unmount, and the overlay's per-vehicle layers by their components, so 100 disable and enable cycles of either extension leave no layer behind (P7). _(Controller.)_

**The flight overlay's per-vehicle reads** go through a new read-only export, each system's home, typed `Readonly` as `telemetry` is. The overlay keeps resolving the map eagerly in `activate()` as it does today, so it still fires no new `docs/out-of-scope.md` trigger: it is the one eager registrant the rows already name. _(Controller.)_

### Click rule

N2 selects by clicking a vehicle, N4 adds Go To and mission editing, N5 points a camera and N11 sets a position fix by clicking the map. A stray click that reaches the wrong one of these commands a vehicle, so the map decides who gets each click, and exactly one receiver gets it. _(Controller.)_

1. **The map owns pointer input on its canvas.** An extension attaches no pointer handlers to the MapLibre instance it reaches through the `gcscode.map.maplibre` context, nor to anything it draws at map coordinates (sources, layers, markers, popups), and a DOM element it places at map coordinates sets `pointer-events: none`, as the heading line does today. It receives clicks there only through the surface below. A registered map control keeps its own pointer events: `packages/extension-map/src/map-view.svelte` puts the control slots beside the canvas element, not inside it, so a control's clicks never reach the canvas (PR #79 EA-11, RT-15). Nothing enforces this in code, as nothing enforces the context key; the map's README states it, and `docs/out-of-scope.md` records the gap (propagation below). _(Controller, in review: PR #79 EA-3.)_
2. **One receiver per click, in this order:** the active tool; else, on a vehicle symbol, selection; else, on another extension's item, that item's information; else nothing. Panning and zooming are never a click. _(Controller, in review: PR #79 EA-12, RT-8.)_
3. **A map tool takes a click only while the operator has turned it on.** A tool is a named contribution, such as "Go to point" or "Set position fix", that the operator starts explicitly from a control or a command. At most one tool is active: starting one ends the other. While a tool is active the map shows its name and a way out, which always works; Escape also ends it while the map view has focus, handled by the view itself as the quick pick handles its keys (`packages/shell/src/quick-pick/quick-pick.svelte`), not as a host keybinding, which would end the tool from any panel and claim Escape app-wide (PR #79 EA-4). A tool declares whether it targets a vehicle. The map hands it the clicked point, and a tool that targets a vehicle also gets the one vehicle rule 6 settles; what the tool does then, including the confirmation N4 requires, is the tool's.
4. **Selection.** With no tool active, a click on a vehicle symbol selects that vehicle once N2 brings selection, and does nothing before.
5. **An item's information.** An item another extension draws may take a click that only shows information about it, such as an aircraft's details under N12, never one that acts on a vehicle; that path is built by its first consumer (Deferred, VS Code alignment).
6. **Overlaps are never resolved by draw order.** Vehicles share a launch pad, and every SITL vehicle starts at one home (roadmap N8), so a click can land on several symbols, or several items. Within one rank of rule 2, the receiver is never picked because it draws on top: when the receiver needs one vehicle (selection, or a tool that targets a vehicle) and more than one symbol is under the point, the map asks the operator which one, and likewise between several items' information. A tool that needs only the point, such as "Go to point" over a shared pad, gets no question. _(Controller, in review: PR #79 EA-5, RT-14.)_

So, for extensions that follow rule 1, a click never acts on a vehicle unless the operator has just chosen a tool that does so, and the map always shows which tool that is. Hover and drag are left to the first consumer that needs them.

**Left to the builder:** exact type and member names; the symbol's shapes per airframe (SITL flies only copters); the stale look, within Goal 6's constraint; the notices' wording and corner; how the home export is shaped.

## Known unknowns

- **The 2 s limit** is S1's proposed position limit, not a measurement. A vehicle whose `GLOBAL_POSITION_INT` stream is slower than that greys in normal flight; ArduPilot's default stream rates send it faster. Revisit if a SITL vehicle flickers stale.
- **No position at exactly 0°, 0°.** Reading both-zero as "no position" is a heuristic: a vehicle with a real position at exactly 0, 0 would not be drawn, and one whose autopilot reports a position before it is trustworthy would be. A fix type from `GPS_RAW_INT` or the EKF's own flags would be firmer, at the cost of another message in the bridge filter. Revisit if a vehicle is ever drawn somewhere it is not (PR #79 RT-1).
- **The Map input view and GCS-14's rung.** The owner settled this on 2026-11-24: a new rung adds its own proof and leaves older proof views alone, and an old view changes only when the new rung clearly grows the same thing, with its smoke test updated in the same PR. GCS-62's proof is P1's probe (Delivery), not a grown Map input view, so the view and its tracker stay as GCS-14 shipped them, and the provider parses its own frames (Goal 4). GCS-14's deferred "one parser" finding therefore stays open; it is GCS-14's to take up if a later rung grows that view. The view's line naming the merged store's last writer stays true of the merged store, but no longer names the vehicle the map draws, so the first PR corrects only the known-issue sentence in `docs/smoke-tests.md` § Map input view, which says GCS-62 fixes it (PR #79 RT-4, RT-13). _(Owner, after review.)_
- **What a layer gets from the map: raw MapLibre, or `map-gl-svelte`.** Today a registered layer reaches the raw MapLibre `Map` through the `gcscode.map.maplibre` context and drives it imperatively. `libs/map-gl-svelte` is a finished Svelte port of react-maplibre (`Map`, `Source`, `Layer`, `Marker`, `Popup`, controls, camera sync that does not fight gestures) and could underpin the map extension, so that layers declare sources and layers as components instead. That would make the library part of gcscode's public map API, with its versioning and its upstream's shape, where today only MapLibre's is. The owner has not decided. The symbol contract does not depend on the answer: a provider returns data, not a component. The layering rule (Goal 3) and the click rule (rule 1) do: the map holds them only as far as it owns what layers draw with, so over raw MapLibre they rest on convention and the README, and a declarative layer API could enforce them. The choice belongs to the spec that rebuilds the map's view or its layer API, or to the "Polish the map extensions" work if it takes it up first (PR #79 EA-1).
- **Home and range in the contract.** They stay in the MAVLink add-on because no second protocol needs them. Revisit when a second protocol's vehicles are drawn, or when N4 or N11 needs a vehicle's home from the map's contract.
- **Shapes other than the copter's** are drawn but never seen in SITL. A unit test with a fake provider covers them.
- **No style, no vehicles.** With the drone icon, heading line and home marker all style layers, nothing of a vehicle draws until the map's style loads, and the style comes from the tile host (`packages/extension-map/src/map-view.svelte`); today's DOM drone marker still draws on a blank canvas. P5 is GCS-64's: it falls back to an empty local style when the tile host's style fails, so vehicles draw on a blank grid (PR #79 RT-12).
- **Five vehicles at telemetry rate.** One GeoJSON source updated for every position frame may cost more than one `setData` per animation frame; the builder batches per frame if P1's frame budget needs it. P2's load test is GCS-67's.
- **GCS-14's other deferred findings**, carried by GCS-62: a changed connection URL resets the home lookup but keeps the old rows; a home read from the bridge is timed by the bridge's clock; the comment in `packages/extension-mavlink/src/asset-adapter.ts` does not list `HOME_POSITION`; a failed read of the stored home is not retried until reconnect. The first PR fixes them, as the owner put them on GCS-62: they are defects of the view as GCS-14 shipped it, not growth, and Goal 5 reads each vehicle's home from the same lookup. The tracker keeps its own clock; only the symbol contract uses Goal 2's.
- **Left by the review for the first PR's plan.** PR #79 RT-16: P1's probe also fails when a system whose autopilot has a stored `GLOBAL_POSITION_INT` away from 0°, 0° has no feature, so a vehicle the map leaves out cannot pass. PR #79 RT-17: a first PR that lands before vehicle status's makes the edits Design lists under "MAVLink's provider" for that case; this spec's propagation sections do not repeat them.

## Delivery

Two feature PRs, in order, each on a `claude/` branch labelled `feat`:

1. **GCS-62, each vehicle's symbol from its own data:** the contract, the map's symbol and heading-line layers, MAVLink's provider and its per-system `GLOBAL_POSITION_INT` parse, the overlay's per-vehicle home and range layers with its drone icon and heading line removed, "Show All Vehicles", and GCS-14's deferred findings. It also builds P1's probe: an automated check that compares each feature in the map's GeoJSON source with that system's own frames, read without going through the MAVLink extension (mavlink2rest's stored copy of the system's `GLOBAL_POSITION_INT`, whose address `packages/extension-mavlink/src/home-seed.ts` already builds) and matched to the feature by the asset's `localId`, so a provider that answers from another system's frames or from the merged store fails it; the provider's updates may still time the one-frame budget (PR #79 RT-11, EA-10). If the probe is also a view an operator opens, it brings its smoke test in `docs/smoke-tests.md`. Done when P1 passes with two SITL vehicles flying apart, and P7 holds for both the map's layers and the overlay's per-vehicle layers (PR #79 RT-10).
2. **GCS-63, a stale vehicle looks stale:** the map's clock and the stale look. Done when P6 passes, a disarmed vehicle included.

The click rule waits for its first consumer, N2 or N4, whose spec builds the surface against it. Builds on the vehicle status contract's first PR for MAVLink's provider clock and per-system record, or brings both itself if it lands first (Design).
